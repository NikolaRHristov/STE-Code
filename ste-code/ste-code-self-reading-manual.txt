# STE-Code: Simplified Technical English for Code
## Self-Reading Manual — Issue 1, July 2026

---

## S0: How to Use This Manual

This manual teaches you to read, understand, and apply the STE-Code specification —
a controlled language for software documentation, API design, commit messages,
code reviews, README files, and inline comments. STE-Code is a proper subset of
English, just as ASD-STE100 is a proper subset of English.

**Self-reading protocol:**

1. Read each section (S0 through S8) sequentially.
2. At the end of each section, answer the self-check questions before continuing.
3. Internalize both the rules AND their rationale — STE-Code is prescriptive, not descriptive.
4. When you encounter a non-STE-Code input, apply the 6-pass transformation pipeline (S2.6)
   to produce compliant output.
5. Return to S2 (Knowledge Base) whenever you need exact rule wording.

**What STE-Code governs:**
- Variable, function, class, and module names
- API documentation and endpoint descriptions
- Commit messages and pull request descriptions
- Inline code comments and docstrings
- Code review feedback
- README files and technical documentation
- Error messages and log output
- Architecture decision records (ADRs)

**What STE-Code does NOT govern:**
- Actual source code syntax (that is the compiler's domain)
- Programming language keywords (these are quoted text)
- Non-English documentation
- Creative or marketing copy

---

## S1: Core STE-Code Principles

STE-Code adapts all 53 writing rules from ASD-STE100 Issue 9 to the
software engineering domain. The core principles are:

1. **Approved Vocabulary Only** — Use only words approved in the STE-Code dictionary
   or that qualify as Technical Code Nouns/Verbs.

2. **One Word, One Meaning** — Every approved word has exactly one approved meaning
   in code contexts. No polysemy without explicit resolution.

3. **Short, Clear Statements** — Maximum 20 words per procedural sentence (commit
   messages, instructions), 25 words per descriptive sentence (documentation).

4. **Active Voice** — Use active voice in all procedural code documentation.
   Passive voice permitted only in descriptive text when the agent is unknown.

5. **Single Instruction Per Sentence** — Each sentence contains exactly one instruction
   unless two actions occur simultaneously.

6. **Technical Code Nouns** — Framework names, library names, class names, module names,
   and API endpoints are Technical Code Nouns. Use them consistently.

7. **Technical Code Verbs** — Operations like `serialize`, `deserialize`, `render`,
   `validate`, `dispatch`, `resolve`, `deploy` are Technical Code Verbs subject to
   the same rules as approved verbs.

8. **No Jargon or Slang** — No regional coding slang, no team-specific abbreviations
   without definition. "DTO," "DAO," "POJO" must be defined on first use.

9. **Consistent Terminology** — Once you name a component `UserService`, never call it
   `UserManager` or `UserHandler` elsewhere in the same context.

10. **Safety Patterns** — Use WARNING for breaking changes, CAUTION for deprecation,
    NOTE for informative context. Follow the safety instruction rules (S2.7).

11. **Vertical Lists for Complexity** — Use bullet or numbered lists when a statement
    has multiple conditions, steps, or alternatives.

12. **Articles Before Nouns** — Use "the," "a," or "an" before code nouns to resolve
    ambiguity. "Call `validate()` on the request object" not "Call validate on request."

13. **No Phrasal Verbs** — Do not combine approved verbs with prepositions to create
    new meanings. "Set up" is not permitted; use "configure" or restructure.

14. **Inclusive Language** — Use gender-neutral terms. No "guys," "he/she,"
    "man-hours." Use "they," "person-hours," "team."

## S2: Knowledge Base

### S2.1: Section 1 — Identifiers and Names (Rules 1.1–1.14)

**Rule 1.1** — Use identifiers that are:
- Approved in the STE-Code vocabulary
- Technical Code Nouns
- Technical Code Verbs

In STE-Code, an "identifier" is any name you assign: variable names, function names,
class names, module names, package names, and API endpoint paths. Use the approved
vocabulary first. When no approved word fits, use a Technical Code Noun or Verb.

*Non-STE-Code:* `function doTheThing(data) { ... }`
*STE-Code:* `function processPayload(payload) { ... }`

**Rule 1.2** — Use approved vocabulary words only as their specified part of speech.

"Validate" is an approved verb. Do not use it as a noun ("run the validate").
Instead: "Run the validation function."

*Non-STE-Code:* `// Do the validate on input`
*STE-Code:* `// Validate the input`

**Rule 1.3** — Use approved words only with their approved meanings.

The approved meaning of "resolve" in STE-Code is "determine the final value of a
promise, future, or deferred computation." You cannot use "resolve" to mean
"fix a bug" — use "fix" instead.

*Non-STE-Code:* `// Resolve the merge conflict`
*STE-Code:* `// Fix the merge conflict`

**Rule 1.4** — Use only the approved forms of verbs and adjectives.

| Verb | Infinitive | Present | Past | Past Participle |
|------|-----------|---------|------|-----------------|
| DEPLOY | deploy | deploys | deployed | deployed |
| SERIALIZE | serialize | serializes | serialized | serialized |
| RESOLVE | resolve | resolves | resolved | resolved |
| VALIDATE | validate | validates | validated | validated |

Adjectives use their base form. Comparatives and superlatives with "more"/"most"
are permitted since "more" and "most" are approved words.

**Rule 1.5** — You can use words that you can include in a Technical Code Noun category.

STE-Code provides 19 categories of Technical Code Nouns (adapted from ASD-STE100):

| Category | Original STE | STE-Code Adaptation |
|----------|-------------|---------------------|
| 1 | Official parts information | Language keywords and reserved words |
| 2 | Vehicles/machines | Frameworks and runtimes |
| 3 | Tools and support equipment | Development tools and build systems |
| 4 | Materials and consumables | Dependencies and packages |
| 5 | Facilities and infrastructure | Deployment targets and environments |
| 6 | Systems and components | Modules, classes, and components |
| 7 | Mathematical/scientific terms | Algorithmic and computational terms |
| 8 | Navigation terms | Routing, pathing, and traversal terms |
| 9 | Numbers/units/time | Data sizes, time units, numeric formats |
| 10 | Quoted text | String literals, error messages, log text |
| 11 | Persons/groups/organizations | Roles, teams, and services |
| 12 | Parts of the body | UI/UX interaction and accessibility terms |
| 13 | Personal effects | Configuration and preference terms |
| 14 | Medical terms | Error states, exceptions, and diagnostics |
| 15 | Official documents | Specification files and config formats |
| 16 | Environmental conditions | Runtime conditions and states |
| 17 | Colors | Terminal colors, syntax highlighting tokens |
| 18 | Damage terms | Bug, defect, and failure taxonomy |
| 19 | IT and telephony terms | Network, protocol, and API terms |
| — | (categories 20-22 from STE) | Merged into relevant categories above |

**Rule 1.6** — Use a word that is not approved in the vocabulary only when it is a
Technical Code Noun or part of a Technical Code Noun.

*Non-STE-Code:* `// The main branch is protected`
*STE-Code:* `// The primary branch is protected`

But "main" is a Technical Code Noun in `main()` function context.

**Rule 1.7** — Do not use Technical Code Nouns as verbs.

"Cache" is a Technical Code Noun (category 6). Do not use "cache" as a verb.
Instead: "Store the result in the cache."

*Non-STE-Code:* `// Cache the response`
*STE-Code:* `// Store the response in the cache`

**Rule 1.8** — Use Technical Code Nouns that are approved in your organization,
ecosystem, or subject field.

If your team calls it `PaymentGateway`, do not call it `PaymentProcessor` or
`PaymentHandler`. Use the approved organizational term.

**Rule 1.9** — When you must select a Technical Code Noun, use one that is short
and easy to understand. Maximum three words.

*Non-STE-Code:* `UserAuthenticationCredentialValidationService`
*STE-Code:* `AuthService` or `CredentialValidator`

**Rule 1.10** — Do not use regional, slang, or jargon words as Technical Code Nouns.

*Non-STE-Code:* `// The foo bar baz pattern`
*STE-Code:* `// The adapter pattern`

**Rule 1.11** — Do not use different Technical Code Nouns for the same item.

If you introduce `EmailService`, always call it `EmailService`. Never switch to
`MailService`, `EmailSender`, or `MessageDispatcher` for the same component.

**Rule 1.12** — You can use verbs that you can include in a Technical Code Verb category.

STE-Code Technical Code Verb categories (adapted from STE):

1. **Development operations:**
   a) Build and compilation: compile, link, transpile, bundle, minify, optimize
   b) Testing: test, assert, mock, stub, spy, verify, coverage
   c) Version control: commit, push, pull, merge, rebase, branch, tag, cherry-pick
   d) Deployment: deploy, release, rollback, scale, provision, configure

2. **Data operations:**
   a) Input/Output: read, write, parse, emit, stream, buffer, flush
   b) Serialization: serialize, deserialize, marshal, unmarshal, encode, decode
   c) Persistence: persist, save, load, query, index, migrate, seed
   d) Transformation: map, filter, reduce, transform, convert, normalize

3. **Application operations:**
   a) Request handling: route, dispatch, handle, serve, respond, redirect
   b) State management: initialize, mount, unmount, hydrate, reconcile, invalidate
   c) Authentication: authenticate, authorize, sign, verify, encrypt, decrypt
   d) Scheduling: schedule, enqueue, dequeue, retry, cancel, timeout

4. **Communication operations:**
   a) Messaging: publish, subscribe, broadcast, emit, receive, acknowledge
   b) Remote calls: request, fetch, invoke, call, subscribe, unsubscribe

**Rule 1.13** — Do not use Technical Code Verbs as nouns.

"Deploy" is a Technical Code Verb. Do not use "deploy" as a noun.
Instead: "Start the deployment" (using "deployment" as the Technical Code Noun).

**Rule 1.14** — Use American English spelling in all identifiers and documentation.

*Non-STE-Code:* `colour_scheme`, `initialise`, `authorise`
*STE-Code:* `color_scheme`, `initialize`, `authorize`

### S2.2: Section 2 — Compound Identifiers (Rules 2.1–2.2)

**Rule 2.1** — Write compound identifiers of no more than three components.

A "component" in a compound identifier is a semantic unit, regardless of casing
convention. `user_email_validator` has three components. `UserEmailValidatorService`
has four — too many.

*Non-STE-Code:* `AbstractUserAuthenticationCredentialValidationServiceFactory`
*STE-Code:* `AuthCredentialFactory` or `UserAuthFactory`

**Rule 2.2** — When a Technical Code Noun has more than three components,
write it in full once. Then give a shorter form.

```
Full: AbstractUserAuthenticationCredentialValidationService
Short form: AuthCredentialValidator (hereinafter "the validator")
```

### S2.3: Section 3 — Functions and Operations (Rules 3.1–3.7)

**Rule 3.1** — Use only the function signature forms given in the approved vocabulary.

Each approved verb maps to a canonical function signature pattern:

| Verb | Signature Pattern |
|------|------------------|
| VALIDATE | `validate(input) -> Result` |
| SERIALIZE | `serialize(object) -> string` |
| PARSE | `parse(raw) -> AST` |
| RENDER | `render(template, context) -> string` |
| QUERY | `query(criteria) -> ResultSet` |

**Rule 3.2** — Use only these function patterns:
- Pure functions (no side effects) — equivalent to infinitive
- Command functions (imperative) — equivalent to command form
- Present tense descriptions — equivalent to simple present
- Past tense for historical/log data — equivalent to simple past
- Future tense for scheduled operations — equivalent to simple future
- Past participle as a state descriptor — equivalent to past participle as adjective

**Rule 3.3** — Use the past participle form as a state descriptor.

*Non-STE-Code:* `// The data that was validated by the service`
*STE-Code:* `// The validated data`

**Rule 3.4** — Do not use complex nested function compositions.

*Non-STE-Code:* `// The function that has been being processed`
*STE-Code:* `// The processing function` or `// The function in process`

**Rule 3.5** — Use the `-ing` form of a verb only as a Technical Code Noun
or as a modifier in a compound identifier.

*Permitted:* `ProcessingQueue` (Technical Code Noun), `streaming response` (modifier)
*Not permitted:* "The function is processing the data" — use "The function processes the data."

**Rule 3.6** — Use the active voice. In descriptive documentation, you can use the
passive voice only when the agent is unknown.

*Non-STE-Code:* `// The request should be validated by the middleware`
*STE-Code:* `// The middleware validates the request.`

*Permitted passive:* `// The request was received at 14:32:07 UTC.` (agent unknown)

**Rule 3.7** — Use an approved verb to describe an action, not a noun.

*Non-STE-Code:* `// Perform validation of the input`
*STE-Code:* `// Validate the input`

### S2.4: Section 4 — Statements and Expressions (Rules 4.1–4.5)

**Rule 4.1** — Write short and clear statements.

*Non-STE-Code:*
```
// To process the payment, first validate the request body to ensure all
// required fields are present, then call the payment gateway with the
// sanitized data, and finally update the order status in the database.
```

*STE-Code:*
```
// 1. Validate the request body.
// 2. Send the sanitized data to the payment gateway.
// 3. Update the order status in the database.
```

**Rule 4.2** — Do not omit words or use contractions.

*Non-STE-Code:* `// Don't use this fn w/out auth token`
*STE-Code:* `// Do not use this function without an authentication token.`

**Rule 4.3** — Use a vertical list for complex texts.

*Non-STE-Code:*
```
// The API returns a 200 for success, 400 for bad request when validation
// fails or the payload is malformed, 401 for unauthorized when the token is
// expired or missing, and 500 for internal server error.
```

*STE-Code:*
```
// The API returns these status codes:
// - 200: Success
// - 400: Bad request (validation failure or malformed payload)
// - 401: Unauthorized (expired or missing token)
// - 500: Internal server error
```

**Rule 4.4** — Use connecting words to link related statements.

Approved connectors: and, or, but, however, therefore, thus, because, if, when,
after, before, while, although, unless, until, so that.

*STE-Code:*
```
// Call the validate function. If the validation succeeds, call the process
// function. However, if the validation fails, return an error.
```

**Rule 4.5** — Use an article (the, a, an) or a demonstrative adjective (this, these)
before a Technical Code Noun.

*Non-STE-Code:* `// Call validate on request`
*STE-Code:* `// Call validate on the request`

### S2.5: Section 5 — Procedural Code Documentation (Rules 5.1–5.5)

**Rule 5.1** — Write short sentences. Maximum 20 words per procedural sentence.

Procedural documentation includes: commit messages, step-by-step instructions,
setup guides, deployment runbooks, and code review action items.

*STE-Code commit message:*
```
Fix race condition in the connection pool

Acquire the mutex before checking the connection state.
Release the mutex after the state is updated.
```
(9 words, 14 words, 10 words — all under 20)

**Rule 5.2** — Write only one instruction per sentence unless two or more actions
occur at the same time.

*Non-STE-Code:*
```
// Install the dependencies and then start the development server and open
// the browser to localhost:3000.
```

*STE-Code:*
```
// 1. Install the dependencies.
// 2. Start the development server.
// 3. Open the browser at http://localhost:3000.
```

*Permitted simultaneous actions:*
```
// Run the linter and the type checker at the same time.
```

**Rule 5.3** — Write instructions in the imperative (command) form.

*Non-STE-Code:* `// You should call the init function first`
*STE-Code:* `// Call the init function first.`

**Rule 5.4** — When there is a condition the reader must know first, start with a
descriptive statement, then give the command separated by a comma.

*STE-Code:*
```
// If the database is not available, retry the connection after 5 seconds.
```

**Rule 5.5** — Write notes only to give information, not instructions.

*Permitted:* `NOTE: The default timeout is 30 seconds.`
*Not permitted:* `NOTE: Set the timeout to 30 seconds.` — this is an instruction.

### S2.6: Section 6 — Declarative Code Documentation (Rules 6.1–6.6)

**Rule 6.1** — Give information gradually.

*STE-Code:*
```
// The AuthService is responsible for user authentication.
// It validates credentials against the configured identity provider.
// It issues a JWT token on successful authentication.
// The token expires after 24 hours.
```

**Rule 6.2** — Use key words and key phrases to give your text a logical structure.

Key phrases: "is responsible for," "has these properties," "returns," "accepts,"
"requires," "depends on," "implements," "extends."

*STE-Code:*
```
// The PaymentProcessor has these properties:
// - It accepts a PaymentRequest object.
// - It validates the payment method.
// - It returns a PaymentResult object.
```

**Rule 6.3** — Write short sentences. Maximum 25 words per descriptive sentence.

**Rule 6.4** — Use paragraphs to show related information.

**Rule 6.5** — Make sure that each paragraph has only one topic.

**Rule 6.6** — Make sure that no paragraph has more than six sentences.

### S2.7: Section 7 — Error Handling and Safety Patterns (Rules 7.1–7.3)

In STE-Code, safety instructions adapt the WARNING/CAUTION/NOTE pattern:

- **BREAKING:** The reader must know that an API change will break existing consumers.
  Equivalent to WARNING (risk of injury/death in original STE).

- **DEPRECATED:** The reader must know that a feature will be removed in a future version.
  Equivalent to CAUTION (risk of damage in original STE).

- **NOTE:** Informative context that does not indicate risk.

**Rule 7.1** — Use an applicable word (BREAKING, DEPRECATED, or NOTE) to identify
the level of impact.

*STE-Code:*
```
## BREAKING: `authenticate()` now requires a `tenantId` parameter

The `authenticate()` method signature changed. You must supply a `tenantId`
parameter. Existing call sites that do not supply this parameter will fail
at compile time.
```

**Rule 7.2** — Start a safety instruction with a clear and accurate command or condition.

*STE-Code:*
```
## DEPRECATED: `UserService.findByEmail()` is deprecated

Use `UserRepository.search({ email })` instead. `findByEmail()` will be
removed in version 4.0.0.
```

**Rule 7.3** — Give an explanation to show the risk or possible result.

*STE-Code:*
```
## BREAKING: The default port changed from 8080 to 3000

Update your configuration. If you do not update the port, your application
will not connect to the service.
```

### S2.8: Section 8 — Syntax and Formatting (Rules 8.1–8.7)

**Rule 8.1** — Use all standard English punctuation marks. Do not use the semicolon (;)
in documentation text.

*Non-STE-Code:* `// The function returns a Result; it may be an error.`
*STE-Code:* `// The function returns a Result. The result can be an error.`

**Rule 8.2** — Use hyphens (-) to connect words that are directly related.

*STE-Code:* `// Use a well-known algorithm.`

**Rule 8.3** — You can use parentheses:
- To reference files or functions: `(see auth.go)`
- To include type annotations: `validate(input: Request) -> Result`
- To give alternative terms: `The service (or "the provider")`
- To include abbreviations: `JSON Web Token (JWT)`

**Rule 8.4** — In a vertical list, a colon (:) has the same effect on word count
as a period and shows the end of a sentence.

**Rule 8.5** — When you put text in parentheses, it counts as one word in that sentence.

**Rule 8.6** — Count each of these as one word:
- Numbers: `404`
- Numbers with units: `500ms`, `2GB`
- Abbreviations: `API`, `JSON`, `JWT`
- Alphanumeric identifiers: `UserService`, `auth-middleware`
- Quoted text: `"connection refused"`
- Titles and headings: `## Installation Guide`
- Proper nouns: `GitHub`, `Docker`, `Kubernetes`

**Rule 8.7** — Hyphenated words count as one word.
`request-response`, `client-server`, `read-only` each count as one word.

### S2.9: Section 9 — Coding Practices (Rules 9.1–9.4, GR-1–GR-8)

**Rule 9.1** — Use a different sentence construction when a word-for-word
replacement is not sufficient.

*Non-STE-Code:* `// The API is broken when the token expires.`
*STE-Code:* `// The API returns an error when the token expires.`

**Rule 9.2** — Use each approved word correctly. Refer to the dictionary for
approved meanings.

**Rule 9.3** — Do not make phrasal verbs by combining verbs and prepositions.

*Non-STE-Code:* `// Set up the database.` `// Tear down the test suite.`
*STE-Code:* `// Configure the database.` `// Remove the test fixtures.`

**Rule 9.4** — Use a consistent style. Once you select a term, use it throughout.

### General Recommendations

**GR-1 — The conjunction "that":**
Use "that" to introduce a subordinate clause when it removes ambiguity.
*STE-Code:* `// Make sure that the connection is open.`

**GR-2 — The preposition "with":**
Use "with" to show an instrument or accompaniment, not to create phrasal verbs.

**GR-3 — Use pronouns carefully:**
Prefer explicit names over pronouns. When you use a pronoun, make sure the
referent is clear. "It" must refer to the most recent noun.

**GR-4 — The pronoun "this":**
Always follow "this" with the noun it refers to. "This function," not "this."

**GR-5 — False friends:**
Be aware of words that look similar but have different meanings in code contexts.
"Argument" (function parameter) vs. "argument" (disagreement).
"Class" (OOP construct) vs. "class" (category/quality).
"Interface" (type definition) vs. "interface" (boundary between systems).

**GR-6 — Latin abbreviations:**
Do not use "e.g.," "i.e.," "etc." Use "for example," "that is," "and so on."

**GR-7 — Inclusive language:**
Use gender-neutral terms. No "guys," "he/she," "man-hours."
Use "they," "person-hours," "team members."

**GR-8 — Possessive form:**
Avoid the Saxon genitive ('s) for inanimate objects in formal documentation.
*Non-STE-Code:* `// The function's return value`
*STE-Code:* `// The return value of the function`

### S2.10: The 6-Pass Transformation Pipeline

To transform non-STE-Code text into STE-Code compliant output, apply these six passes:

**Pass 1 — Lexical Lookup:**
Tokenize the input. Match each word against the STE-Code dictionary.
Mark words as: APPROVED, UNAPPROVED, TECHNICAL_NOUN, TECHNICAL_VERB, UNKNOWN.

**Pass 2 — Classification:**
Classify each UNKNOWN word. Can it fit in a Technical Code Noun category (Rules 1.5–1.6)?
Can it fit in a Technical Code Verb category (Rule 1.12)?
If yes, reclassify it. If no, mark for replacement.

**Pass 3 — Part-of-Speech Lock:**
Verify that each APPROVED word is used as its specified part of speech.
If a Technical Code Noun is used as a verb (Rule 1.7 violation), restructure.
If a Technical Code Verb is used as a noun (Rule 1.13 violation), restructure.

**Pass 4 — Meaning Validation:**
Verify that each approved word is used with its approved meaning.
Apply the polysemy resolution table. If a word has multiple approved meanings,
select the one that matches the context.

**Pass 5 — Grammar Enforcement:**
Apply verb form restrictions (Rules 3.1–3.5).
Apply voice restrictions (Rule 3.6).
Apply sentence length limits (Rules 5.1, 6.3).
Apply compound identifier limits (Rules 2.1–2.2).

**Pass 6 — Consistency Check:**
Verify that the same Technical Code Noun is used consistently (Rule 1.11).
Verify that the same terminology is used throughout (Rule 9.4).
Verify that no jargon, slang, or regional terms remain (Rule 1.10).

## S3: Page-Reading Protocol

When you process a document page by page:

1. **Identify the document type:** README, API spec, code review, commit message,
   architecture decision record, or inline comment.

2. **Extract all identifiers:** Variable names, function names, class names, module names.
   Check each against the STE-Code vocabulary.

3. **Extract all actions:** What does the code do? Map each action to an approved verb.

4. **Check sentence length:** Count words per sentence (using Rules 8.4–8.7 for word counting).

5. **Apply the 6-pass pipeline** to the extracted text.

6. **Output the STE-Code compliant version** in the standard output format (S7).

## S4: Skill Extraction Framework

From any code document, extract these skill dimensions:

1. **Vocabulary skill:** Can the reader identify approved vs. unapproved words?
2. **Classification skill:** Can the reader classify Technical Code Nouns and Verbs?
3. **Restructuring skill:** Can the reader transform non-compliant sentences?
4. **Consistency skill:** Can the reader detect inconsistent terminology?
5. **Safety skill:** Can the reader apply BREAKING/DEPRECATED/NOTE correctly?

---

## S5: Code-Specific Extraction (Adapted from UML)

For code architecture documents, extract:

1. **Components:** Classes, modules, services — Technical Code Nouns (category 6).
2. **Dependencies:** Imports, requires, uses — Technical Code Nouns (category 4).
3. **Interfaces:** API contracts, type signatures — quoted text (category 10).
4. **Data flow:** What functions call what — Technical Code Verbs.
5. **State transitions:** Lifecycle events — use past participle forms (Rule 3.3).
6. **Error paths:** Exception types, error codes — Technical Code Nouns (category 14).

## S6: Recursive Questioning Protocol

For each statement in a code document, ask these 13 questions:

1. Is every word either approved, a Technical Code Noun, or a Technical Code Verb?
2. Is every approved word used as its specified part of speech?
3. Is every approved word used with its approved meaning?
4. Are all verb forms from the approved list?
5. Does the statement use active voice (or justified passive)?
6. Is there a maximum of one instruction per sentence?
7. Is the sentence under the word count limit (20 procedural / 25 descriptive)?
8. Are compound identifiers under three components?
9. Are Technical Code Nouns used consistently?
10. Are there any phrasal verbs?
11. Are there any contractions, omissions, or Latin abbreviations?
12. Are safety instructions (BREAKING/DEPRECATED) properly formatted?
13. Is the language inclusive?

## S8: Context Window Management

STE-Code is designed for LLM consumption. To manage context:

1. **Short form:** Load the distilled system prompt (~1,200 tokens) as a system message.
2. **Reference mode:** Keep only S2 (Knowledge Base) in context during document processing.
   Load S0–S1 and S7–S8 once at session start.
3. **Streaming mode:** Process one page/section at a time. Discard processed pages.
4. **Multi-turn:** State carries forward the current document type, detected violations,
   and pending transformations.
