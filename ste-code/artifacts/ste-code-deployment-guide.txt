## 1. LLM Integration — How to Use STE-Code with Different Models

STE-Code ships as a system prompt. Copy the prompt text into any LLM that supports system messages. The model then produces documentation that obeys the 14 core principles and 51 writing rules.

### ChatGPT (OpenAI)

Open the ChatGPT web interface or use the API. Paste the distilled system prompt (~1,200 tokens, Level 1) into the system message field. For the API, include it in the messages array:

```python
import openai

response = openai.chat.completions.create(
    model="gpt-4o",
    messages=[
        {"role": "system", "content": open("ste-code-distilled-system-prompt.txt").read()},
        {"role": "user", "content": "Check this README for STE-Code compliance: ..."}
    ],
    temperature=0.3
)
```

### Claude (Anthropic)

Use the Messages API with a system parameter. Claude supports system prompts natively:

```python
import anthropic

client = anthropic.Anthropic()
response = client.messages.create(
    model="claude-sonnet-4-20250514",
    system=open("ste-code-distilled-system-prompt.txt").read(),
    messages=[{"role": "user", "content": "Transform this API doc to STE-Code: ..."}],
    temperature=0.3,
    max_tokens=4096
)
```

### Gemini (Google)

Use the system_instruction parameter in the GenerativeModel constructor:

```python
import google.generativeai as genai

model = genai.GenerativeModel(
    model_name="gemini-2.5-pro",
    system_instruction=open("ste-code-distilled-system-prompt.txt").read()
)
response = model.generate_content("Rewrite this commit message in STE-Code: ...")
```

### DeepSeek

Use the standard chat completions API with the system role:

```python
from openai import OpenAI

client = OpenAI(api_key="...", base_url="https://api.deepseek.com")
response = client.chat.completions.create(
    model="deepseek-chat",
    messages=[
        {"role": "system", "content": open("ste-code-distilled-system-prompt.txt").read()},
        {"role": "user", "content": "Check this docstring: ..."}
    ],
    temperature=0.3
)
```

### Local Models (Ollama)

Create a Modelfile with the system prompt baked in:

```
FROM llama3.2
SYSTEM """
[Full contents of ste-code-distilled-system-prompt.txt]
"""
PARAMETER temperature 0.3
PARAMETER top_p 0.9
```

Then build and run:

```bash
ollama create ste-code -f Modelfile
ollama run ste-code
```

### Local Models (LM Studio)

1. Download a model (Llama 3.2, Mistral, Qwen 2.5).
2. Paste the distilled system prompt into the System Prompt field.
3. Set temperature to 0.3.
4. Save as preset "STE-Code".

### Local Models (llama.cpp)

```python
from llama_cpp import Llama

llm = Llama(model_path="llama3.2.Q4_K_M.gguf", n_ctx=8192)
system_prompt = open("ste-code-distilled-system-prompt.txt").read()

def ste_code_check(text):
    response = llm.create_chat_completion(
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": f"Check this text for STE-Code compliance:\n{text}"}
        ],
        temperature=0.3
    )
    return response["choices"][0]["message"]["content"]
```

### Recommended Temperature

Set temperature to 0.3 for all models. This value balances accuracy (the model follows the rules) with flexibility (the model produces natural output). Lower values (0.0-0.2) cause overly rigid output. Higher values (0.5+) cause rule violations.

## 2. System Prompt Integration — Copy, API, Modelfile

STE-Code provides 6 artifact files. Each file serves a different integration path.

| File | Size | Integration Method |
|------|------|--------------------|
| ste-code-distilled-system-prompt.txt | ~1,200 tokens | Copy-paste into any LLM system prompt field |
| ste-code-self-reading-manual.txt | ~7,000 tokens | Load as additional context for 16K+ models |
| ste-code-extraction-methodology.txt | ~1,400 tokens | Reference for reproducibility audit |
| ste-code-example-turn.txt | ~500 tokens | Quick start example for evaluation |
| ste-code-deployment-guide.txt | This file | Integration instructions |
| README.md | ~500 tokens | Artifact index |

### Integration Methods

**Method A: Copy-Paste (Quickest).** Open the distilled system prompt file. Copy all text. Paste into the system prompt field of ChatGPT, Claude, Gemini, or LM Studio. Start writing documentation. The model now produces STE-Code compliant output.

**Method B: API (Programmatic).** Load the system prompt from disk. Include it as the system message in every API call. See the code examples in Section 1 for each provider.

**Method C: Modelfile (Persistent).** Create an Ollama Modelfile with the system prompt. Build the model once. All future runs use the same system prompt. Works offline.

**Method D: Full Context Load (Maximum Accuracy).** For models with 16K+ context, load the self-reading manual (~7,000 tokens) alongside the system prompt. The model references the full 51 rules, synonym table, and category definitions during each compliance check.

## 3. The 8 Adaptation Levels (-2 through 5)

STE-Code provides 8 loading levels. Each level is a different system prompt file with a different scope and context budget. Choose the level that matches your model's context window and your task.

| Level | Prompt File | Tokens | Context Needed | Use Case |
|-------|------------|--------|----------------|----------|
| -2 | ste-code-micro.md | ~400 | <2K | Emergency fallback. Bare-minimum 5 rules. Use when context is extremely limited. |
| -1 | ste-code-agentic.md | ~800 | <4K | Pipeline worker agents. Rails-only. No vocabulary rules. For agents inside the extraction pipeline. |
| 0 | ste-code-user.md | ~900 | <4K | Human learning. Plain-language introduction. Readable by new contributors. |
| 1 | ste-code-distilled-system-prompt.txt | ~1,200 | 4K+ | **Primary template.** All 14 principles + synonym table. Drop-in for most LLMs. |
| 2 | ste-code-developer.md | ~900 | 4K+ | Standard extension. Rules for adding vocabulary, adapting to new domains, building tooling. |
| 3 | compliance-check.prompt.md | ~500 | 4K+ | CI/CD linter. Parameterized template. Accepts document type, domain, rule subset variables. |
| 4 | ste-code-full.md | ~3,000 | 8K+ | Maximum rules. All 51 rules loaded. Best for thorough compliance audits. |
| 5 | ste-code-self-reading-manual.txt | ~7,000 | 16K+ | **Complete reference.** Full manual with all rules, dictionary excerpt, synonym table, examples, and checklist. |

### When to Use Each Level

**Level -2 (Micro):** Use when the model has less than 2K tokens of context budget remaining. Covers the 5 most blocking rules only: approved vocabulary, one term per concept, no noun-as-verb, sentence length, and imperative mood.

**Level -1 (Agentic):** Use for pipeline worker agents that extract, refine, or adapt STE content. Includes 8 hard rails (no fabrication, no truncation, verbatim fidelity), gate transition rules, and the worker lifecycle. Does not include vocabulary rules.

**Level 0 (User):** Use to onboard new team members. Written in plain language. Covers the core ideas, the 5 most important rules, the synonym quick reference, and BREAKING/DEPRECATED/NOTE conventions.

**Level 1 (Distilled):** The default. Use for any LLM with 4K+ context. Covers all 14 core principles, the synonym table, output format rules, and anti-patterns. This is the prompt that ships with every STE-Code release.

**Level 2 (Developer):** Use when extending the standard. Covers the four-stratum architecture, how to add new rules, how to add vocabulary, how to adapt to a new domain, how to update agentic rails, and stratum isolation rules.

**Level 3 (Compliance):** Use in CI/CD pipelines. A parameterized template with variables for document_type, target_domain, rule_subset, and context_size. Loads the synonym table and compliance rubric. Outputs a structured compliance report.

**Level 4 (Full):** Use for thorough audits. Loads all 51 rules plus the complete synonym table. Requires 8K+ context. Best for final review before a major release.

**Level 5 (Manual):** Use for 16K+ context models. The complete self-reading manual. Includes all rule summaries with examples, the dictionary excerpt, the full synonym table, 19 category definitions, and the review checklist.

## 4. CI/CD Integration — Documentation Pipeline

Integrate STE-Code compliance checking into your documentation pipeline. Catch violations before they reach production.

### Pre-Commit Hook

Add a compliance check to your pre-commit configuration:

```yaml
# .pre-commit-config.yaml
repos:
  - repo: local
    hooks:
      - id: ste-code-check
        name: STE-Code Compliance Check
        entry: python3 scripts/ste_code_check.py
        language: python
        files: \.(md|txt|rst)$
        stages: [commit]
```

The check script loads the Level 3 compliance prompt, sends each staged markdown file to the LLM, and parses the compliance report. If the score falls below 80/100, the commit is blocked.

### GitHub Actions

```yaml
# .github/workflows/ste-code.yml
name: STE-Code Compliance
on: [pull_request]

jobs:
  compliance:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run STE-Code check
        run: |
          python3 ste-code/scripts/ci_check.py \
            --docs docs/ \
            --threshold 80 \
            --level 3
```

### Severity-Based CI Behavior

STE-Code violations have four severity levels. Configure your CI pipeline accordingly:

| Severity | CI Behavior | Example |
|----------|------------|---------|
| critical | Fail build, block merge | Fabrication, truncation, gate failure |
| blocking | Fail build, block commit | Unapproved synonym, noun-as-verb, sentence too long |
| warning | Warn, allow merge | American spelling, ambiguous pronoun |
| advisory | Info only | Shorter noun preferred, more established term available |

### Pipeline Architecture

The documentation pipeline has three stages:

1. **Write.** Contributors write documentation normally. No STE-Code constraints during drafting.
2. **Check.** The pre-commit hook or CI workflow runs STE-Code compliance check. Violations are reported with line numbers, corrections, and rule references.
3. **Fix.** Contributors review violations. Blocking violations must be fixed. Warnings should be fixed. Advisories are informational.

## 5. Customization — Extending STE-Code for Specific Domains

Every organization has domain-specific vocabulary. STE-Code supports extensions without modifying the core standard.

### Adding Domain Vocabulary

1. Classify new terms using the vocabulary review prompt: `ste-code/v2/compute/prompts/vocabulary-review.prompt.md`.
2. Add terms to `ste-code/v2/data/exceptions/domain-extensions.json`. Each entry requires:
   - term (the word)
   - type (noun or verb)
   - category-id (1-19 for nouns, 1-4 for verbs)
   - domain (your organization or project name)
   - severity (blocking, warning, or advisory)
   - added-by (your name)
   - added-date (ISO 8601)
   - rationale (why this term is necessary)
3. Tag every vocabulary entry with a domain array. The compliance checker loads only entries tagged with the active domain.

### Adapting to a New Subject Field

1. Run the rule adaptation prompt: `ste-code/v2/compute/prompts/rule-adaptation.prompt.md` with target_domain set to your new domain.
2. Place adapted rules in `ste-code/v2/core/rules/domains/{{domain}}/`.
3. Add domain-specific vocabulary to `ste-code/v2/data/vocabulary/` with the new domain tag.
4. Assemble a new narrative file: `ste-code/v2/narratives/system-prompts/ste-code-{{domain}}-full.md`.
5. Do not modify the code-domain rules in `ste-code/v2/core/rules/`.

### Stratum Isolation

STE-Code v2 architecture has four strata. Customization must respect stratum boundaries:

- `core/` — Immutable rules. Change only when the spec changes.
- `data/` — Living vocabulary. Add terms here without touching rules.
- `compute/` — Logic layer. Checklists, schemas, scoring, prompts.
- `narratives/` — Assembled outputs. Generated from other strata. Never hand-author.

Core never imports from data. Data never imports from core or compute. Compute reads from both. Narratives are assembled, not authored.

## 6. Benchmark — Testing Compliance

STE-Code ships with a benchmark suite that measures compliance against a plain-assistant control group.

### Benchmark Design

The benchmark runs 59 test cases across 14 documentation categories:
- README (5 tests)
- API documentation (5 tests)
- Commit messages (5 tests)
- Error messages (5 tests)
- Code comments (5 tests)
- CHANGELOG entries (3 tests)
- Config file comments (3 tests)
- Composite documents (4 tests)
- Generated functions (4 tests)
- Generated PR reviews (4 tests)
- Generated API docs (4 tests)
- Generated commit messages (4 tests)
- Generated error messages (4 tests)
- Generated README (4 tests)

### Scoring Method

```
correctness = (expected_keywords_found / total_expected) *
               (1 - forbidden_found / total_forbidden)
compliance  = principles_satisfied / total_expected_principles
pass        = correctness >= 0.70
```

### Running the Benchmark

```bash
# STE-Code group (with system prompt)
python3 .agents/benchmark/orchestrator.py

# Control group (plain assistant, no system prompt)
python3 .agents/benchmark/orchestrator-control.py
```

### Published Results (run-20260730-012639)

| Metric | STE-Code | Plain Assistant | Improvement |
|--------|----------|-----------------|-------------|
| Pass rate | 96.6% (57/59) | 11.9% (7/59) | +84.7% |
| Average correctness | 0.941 | 0.471 | +0.448 |

Top 3 categories with the largest improvement:
- Code comments: +0.580
- Error messages: +0.560
- Config file comments: +0.520

Categories with perfect STE-Code scores:
- Commit messages: 1.000 (5/5)
- Generated README: 0.998 (4/4)
- Generated API docs: 0.998 (4/4)

### Interpreting Your Own Benchmark

Run the benchmark on your documentation. Compare the STE-Code score to the plain-assistant score. The difference is the compliance gain from the system prompt. A score below 80/100 means your documentation needs revision. Focus on the highest-weight principles first: approved vocabulary (weight 20) and one term per concept (weight 10).

### Compliance Rubric Weights

| Principle | Weight | Pass Threshold |
|-----------|--------|----------------|
| P1 — Approved Vocabulary | 20 | blocking |
| P11 — One Term Per Concept | 10 | blocking |
| P2 — Term Type Consistency | 8 | blocking |
| P5 — Noun Category Membership | 7 | blocking |
| P7 — No Noun-as-Verb | 7 | blocking |
| P12 — Verb Category Membership | 7 | blocking |
| P13 — No Verb-as-Noun | 7 | blocking |
| Remaining 7 principles | 34 combined | varies |
| **Total** | **100** | **>= 80 to pass** |
