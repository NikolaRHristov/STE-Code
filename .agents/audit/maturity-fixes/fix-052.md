## 10. Error State Machine — Failure Modes and Recovery

```mermaid
stateDiagram-v2
    direction LR

    [*] --> WorkerLaunched

    state WorkerLaunched {
        [*] --> Running : bg process active

    }

    Timeout --> CheckDisk : output file on disk?
    Crashed --> CheckDisk : output file on disk?
    Hangs --> KillProcess : process kill

    state CheckDisk {
        [*] --> FileExists : file present on disk?

        ValidSize --> NoTrunc : no truncation?
        NoTrunc --> UseExisting : ✅ use existing file

    UseExisting --> BatchComplete : mark as done
    FileMissing --> ReLaunch : re-launch same worker
    TooSmall --> SplitPages : split page range in half
    Truncated --> SplitPages : split page range in half

    SplitPages --> SubWorker2 : launch sub-worker (second half)

## Appendix C — Known Limitations and Workarounds

### C.1 — notify_on_complete Reliability

**Limitation:** The pipeline assumes that `notify_on_complete=true` always delivers a notification when a background worker exits. If a notification is dropped by the runtime, the orchestrator waits indefinitely.

**What breaks:** The batch loop hangs at the barrier. The orchestrator never proceeds to verification or the next batch.

**Workaround:** Use a timeout watcher. After 5 minutes with no notification, poll the disk directly. If the output file exists and exceeds 3KB with no truncation markers, accept it as complete. If no file exists, re-launch the worker. See Section 10 (Error State Machine) for the full recovery flow.

### C.2 — 3-Worker Concurrency Limit

**Limitation:** The pipeline launches at most 3 parallel workers per batch. This limit is hardcoded in the batch scheduler (Section 9).

**What breaks if violated:** Launching more than 3 concurrent workers can exceed the model provider rate limit. The `notify_on_complete` mechanism may also drop notifications under high load.

**Rationale:** The limit of 3 balances throughput against reliability. Each worker processes 4 pages of the 434-page spec. With 37 batches of 3 workers, the pipeline completes in a predictable number of rounds.

**To change:** Update the batch size in Sections 2, 3, and 9. Recalculate the batch count as `ceil(109 / new_batch_size)`. Update the Pipeline Summary table. Test with a small batch before full execution.

### C.3 — git gcommit-hermes Dependency

**Limitation:** The pipeline uses `git gcommit-hermes` for commits (Section 2, BatchLoop). This is a custom git alias that must exist in the user's git configuration.

**What breaks:** If the alias does not exist, batch commits fail. The pipeline cannot track progress.

**Workaround:** Set the alias before running the pipeline:

```bash
git config --global alias.gcommit-hermes '!f() { git add -A && git commit -m "$*"; }; f'
```

Or replace `git gcommit-hermes` with `git add -A && git commit -m "batch N"` in all pipeline scripts.

### C.4 — Hardcoded 109-Worker Assumption

**Limitation:** The pipeline assumes exactly 109 workers for a 434-page spec (4 pages per worker). This value appears in the worker grid, progress tracking, gate checks, and the Pipeline Summary table.

**What breaks if changed:** If the source spec changes size, all hardcoded `109` values become incorrect. Gate checks that verify `wc -l → 109` will fail even when the pipeline runs correctly.

**To adapt:** Calculate the new worker count as `ceil(total_pages / 4)`. Replace all `109` references. Recalculate batch count as `ceil(worker_count / 3)`. Update the worker grid. Run GATE 0 checks to confirm the new count.

### C.5 — Single-Threaded Stages 3-5

**Limitation:** Stages 3 (Merge), 4 (Adapt), and 5 (Artifacts) run sequentially in a single agent (Agent #4). They cannot be parallelized within the current architecture.

**Rationale:** Stage 3 requires reading all 109 files in order. Stage 4 depends on the complete merged output. Stage 5 depends on the complete adapted output. These are sequential dependencies by design.

**Impact:** Pipeline throughput is bounded by the slowest of these three stages. For the current 434-page spec, this is acceptable. For a larger spec, consider splitting the merge into sub-batches.
