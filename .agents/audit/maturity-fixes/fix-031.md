## Worked Example: Rule 3.5 (Restrict the -ing form)

This example shows the full adaptation path from original ASD-STE100 aerospace form to STE-Code code-domain form.

### Original Rule (from `merged/master.md`, Section 3)

**Rule 3.5**: Do not use the "-ing" form of a verb unless it is part of a technical name.

**Original aerospace STE example:**
> **STE:** MAKE SURE THAT THE ENGINE STARTS.
> **Non-STE:** MAKE SURE THAT THE ENGINE IS STARTING.

**Original aerospace Non-STE example:**
> **STE:** REMOVE THE COVER.
> **Non-STE:** REMOVING THE COVER.

### Adapted Rule (written to `ste-code/adapted/a-sec3-rule3.5.md`)

**Rule 3.5**: Do not use the "-ing" form of a verb unless it is part of a technical name.

**Code-domain STE example:**
> **STE:** Make sure that the server starts.
> **Non-STE:** Make sure that the server is starting.

**Code-domain Non-STE example:**
> **STE:** Remove the deprecated parameter.
> **Non-STE:** Removing the deprecated parameter.

**Adaptation note**: The constraint is identical — replace continuous/progressive forms with simple imperative or present tense. Code documentation examples replace aerospace maintenance examples. The rule number and rule text do not change because the linguistic constraint is domain-agnostic.

### Additional Example: Rule 7.1 (Safety instructions — two-part structure)

**Original Rule 7.1**: Safety instructions must have a two-part structure: a command (what to do) followed by a consequence (why).

**Original aerospace:**
> **WARNING:** MAKE SURE THAT THE ENGINE IS OFF BEFORE YOU OPEN THE COWL. IF YOU DO NOT OBEY THIS INSTRUCTION, THE FAN BLADES CAN CAUSE INJURY.

**Adapted code-domain:**
> **BREAKING:** Remove all callers of the deprecated function before you delete it. If you do not obey this instruction, the build will fail with unresolved symbol errors.

**Adaptation note**: WARNING maps to BREAKING. The two-part structure (command + consequence) is preserved. The aerospace hazard (fan blade injury) maps to a code hazard (build failure). The "IF YOU DO NOT OBEY" bridge phrase is preserved as it is an approved STE sentence pattern.

## Edge Case Guidance

Handle these situations during adaptation.

### Rules with no obvious code-domain analogue

If a rule concerns a physical-world constraint that has no direct code equivalent, map it to the closest documentation or process constraint.

**Example — Rule 2.1 (Use only approved forms of nouns):** The aerospace domain has approved/unapproved noun forms (e.g., "engine" is approved, "powerplant" is not). In code, map this to: use only approved names for technical concepts. If your codebase uses "handler" for request processors, do not switch to "controller" or "processor" in different files.

**Example — Rule 6.2 (Use the active voice in descriptive writing):** The rule is linguistic, not aerospace-specific. The adaptation is direct: "The function returns a User object" (active, approved) instead of "A User object is returned by the function" (passive, not approved).

### Idiomatic aerospace examples that resist adaptation

Some original examples use domain-specific idioms that do not translate literally.

**Guidance:** Identify the underlying constraint first. Then write a code-domain example that demonstrates the same constraint, even if the surface form differs.

**Example — "BLEED THE HYDRAULIC SYSTEM":** The constraint is "use bleed as an approved technical verb in maintenance procedures." The code-domain analogue is not literal translation. Instead, identify a code-domain verb with the same structural role: "FLUSH THE CACHE" or "PURGE THE QUEUE" — both are approved technical verbs in their respective domains.

**Example — "DE-ICE THE WING":** The constraint is "use de-ice as an approved compound verb for a specific procedure." The code analogue: "DE-SERIALIZE THE PAYLOAD" or "DE-ALLOCATE THE BUFFER" — compound verbs with a specific, approved meaning.

### Rules that are entirely linguistic (no domain content)

Some rules are pure grammar rules with no aerospace-specific content. These require minimal adaptation — only the examples change.

**Rules in this category:** Rule 1.2 (use words only as specified part of speech), Rule 3.2 (use only approved verb tenses), Rule 4.1 (keep sentences short), Rule 5.1 (use imperative mood for instructions), Rule 6.3 (do not omit articles).

**Guidance:** Keep the rule statement unchanged. Replace only the example pairs. The adaptation is mechanical for these rules.

### Cross-domain safety mappings

| Aerospace Hazard | Code-Domain Hazard | Mapping Rule |
|------------------|-------------------|--------------|
| Physical injury | Build failure, runtime crash | Map WARNING → BREAKING |
| Equipment damage | Data loss, API incompatibility | Map CAUTION → DEPRECATED |
| Procedural error | Incorrect configuration | Map safety instruction → validation instruction |
| Environmental hazard | Resource exhaustion, memory leak | Map hazard → performance warning |
