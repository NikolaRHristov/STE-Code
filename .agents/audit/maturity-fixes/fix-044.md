## Edge Case Resolution

These rules help workers classify content when section boundaries blur.
Use them in priority order.

### Dual-Type Pages (RULES+CAT, pages 43-66)

Pages 43-66 contain both rule statements (RULES type) and category lists
(CATEGORIES type). The two content types are interleaved.

Resolution for dual-type pages:

1. Extract all content from the page.
2. Classify each text block as RULES or CATEGORIES.
3. If a block contains a "Rule X.Y" label, classify it as RULES.
4. If a block contains a "Category N:" label, classify it as CATEGORIES.
5. If a block contains both labels, classify as RULES.
6. Flag the block as DUAL-TYPE for auditor review.
7. Write the classified blocks to separate files per type.

If extraction produces fewer than 2 STE/non-STE pairs for a page marked RULES,
the page has category content that the worker must also extract.
Re-extract the page with both RULES and CATEGORIES prompts.

### Overlapping Page Ranges

The RULES type (pages 43-128) and CATEGORIES type (pages 47-66) overlap.
The DICT type range (129-360) is adjacent to the RULES type range.
This overlap is intentional:

- RULES pages 43-46 contain rules only, no categories.
- RULES pages 47-66 contain rules AND categories (dual-type).
- RULES pages 67-128 contain rules only.
- Pages 128-129 may contain a rule ending and dictionary start.

When a worker gets a page range that crosses a section boundary:

1. Check the Quick Lookup table for the exact boundary page.
2. Split the worker page range at the boundary.
3. Assign each sub-range the correct type.
4. If the split leaves a worker with fewer than 2 pages, merge it into
   the adjacent worker range of the same type.

### Workers That Span Two Section Types

A worker may get a batch that spans two types (for example, pages 125-132
covers RULES and DICT). When this occurs:

1. Process pages 125-128 with the RULES extraction prompt.
2. Process pages 129-132 with the DICT extraction prompt.
3. Write output to separate files: `Wxxx-rules.md` and `Wxxx-dict.md`.
4. Add a metadata header to each file:

```
# Type: RULES | Worker: Wxxx | Pages: 125-128
# Split from dual-type batch: 125-132
```

### Pages That Do Not Match Any Type Signature

Some pages in the spec may not match the expected content signature
for their assigned type. For example, a page in the RULES range
that contains only a large diagram with no rule text.

When a page does not match its type signature:

1. Extract all visible text from the page.
2. Check if the page contains only non-text content (diagrams, flowcharts,
   blank space).
3. If the page has no extractable text, write a placeholder file:

```
# Worker: Wxxx | Page: NNN | Type: RULES
# Status: NO TEXT EXTRACTED
# Reason: Page contains only diagram content.
# Action: Flag for manual review.
```

4. Do not invent text for pages with no visible content.
5. Do not skip the page — always produce an output file,
   even if it is a placeholder.

### Continuation Pages (Rule Spans Multiple Pages)

When a rule starts on one page and continues to the next page:

1. Extract the full rule text including the continuation.
2. Mark the page break location with a note:

```
### Rule X.Y (continued from page N)
[continuation text]

> PAGE BREAK: Page N / Page N+1
```

3. Do not split the rule into two entries.

## Failure Recovery Protocol

Use these procedures when extraction fails or produces incomplete output.

### Fewer Than Expected STE/Non-STE Pairs

Each RULES page must produce at least 3 STE/non-STE example pairs.
If a worker returns fewer than 3 pairs for a RULES page:

1. Check if the page contains category content instead of rules.
2. If the page is in the 47-66 range, re-extract with the CATEGORIES
   prompt also.
3. If the page is outside 47-66, re-extract with the `--preserve-columns`
   extraction flag.
4. Compare the two extractions. Use the one with more complete example pairs.
5. If both extractions produce fewer than 3 pairs, flag the page for
   manual review.

### Truncated Output

If a worker output file ends in the middle of a sentence or table row:

1. Check the original page image for the continuation content.
2. Increase the worker token budget by 50%.
3. Re-extract the page.
4. If the second extraction also truncates, split the page:
   - Extract the top half.
   - Extract the bottom half.
   - Merge the two extractions.
5. Check the merged output for duplicate text at the split point.
   Remove any duplicates.

### Missing Pages

If a worker batch is missing one or more pages:

1. Check the page numbering in the input PDF.
2. Check for blank pages between content pages (common in printed specs).
3. If a page is blank, note it:

```
# Worker: Wxxx | Page: NNN
# Status: BLANK PAGE
# Action: No extraction required.
```

4. If a page number is skipped in the PDF (for example, page 200 is missing
   between 199 and 201), note the gap:

```
# Worker: Wxxx | Page: 200
# Status: MISSING FROM PDF
# Action: Check source material for page 200.
```

5. Send a gap report to the coordinator. Do not fill the gap with
   invented content.

### OCR Garbling

The 4-column layout of the DICT section (pages 129-360) causes text
interleaving in OCR output. This is a known issue.

When OCR output shows garbled or interleaved text:

1. Check if the garbling is column interleaving or true OCR errors.
2. For column interleaving:
   - The text is correct but columns are merged.
   - Preserve all text as-is.
   - The Refiner agent will de-interleave columns in Stage 2.
3. For true OCR errors (wrong characters, missing text):
   - Re-extract the page with the `--ocr-engine=v2` flag.
   - Compare with the first extraction.
   - Use the extraction with fewer garbled characters.
4. If both extractions produce garbled text for the same region,
   flag the page for manual review.

### Worker Timeout or Crash

If a worker process stops before producing output:

1. Check the worker log for the last processed page.
2. Restart the worker from the next unprocessed page.
3. If the same page causes a crash again:
   - Split the page processing into smaller chunks.
   - Process one content block at a time.
4. If the crash repeats on the same content block:
   - Skip the block.
   - Note the skip in the output file.
   - Flag for manual review.

## Design Rationale

### Why 8 Section Types

The ASD-STE100 Issue 9 specification has 434 pages organized into
structural sections with distinct content signatures.
The 8-type partition follows the spec's own structural divisions:

1. **FRONT** (pages 1-12): Legal and administrative front matter.
   Needs exact preservation with no summarization because legal text
   must remain verbatim.

2. **TOC** (pages 13-16): Table of contents with page references.
   Needs structure extraction because the TOC is used for page-to-section
   mapping, not for its prose content.

3. **INDEX** (pages 17-24): Subject-to-rule cross-reference table.
   Needs table extraction because the index is a dense tabular resource.

4. **INTRO** (pages 25-42): Introduction and Q&A content.
   Needs full text extraction because the introduction sets context
   for all subsequent rules.

5. **RULES** (pages 43-128): The core rule statements with examples.
   This is the highest-priority section. Each rule has a statement,
   explanatory text, and at least one STE/non-STE example pair.

6. **CATEGORIES** (pages 47-66): Technical noun category definitions.
   These pages define the classification system for technical nouns
   and have a different structure from the rules they sit between.

7. **DICT** (pages 129-360): The approved/unapproved word dictionary.
   This is the largest section (232 pages). It has a dense 4-column
   layout that is the hardest to extract correctly.

8. **APPENDIX** (pages 361-434): Appendices with change history,
   flowcharts, index, and forms. Each appendix has its own structure.

### Alternative Partitions Considered

Three alternative partitions were evaluated:

**Alternative A: 5 types (FRONT, RULES, DICT, APPENDIX, merged INTRO+INDEX+TOC)**

Rejected because: INTRO, INDEX, and TOC have different content signatures
and different extraction requirements. Merging them causes:
- The INDEX table format is lost in prose extraction.
- The TOC page references are not validated.
- Workers cannot apply the right extraction strategy to merged pages.

**Alternative B: 12 types (split DICT into 4 alphabet ranges, split RULES into 3 sub-ranges)**

Rejected because: The DICT alphabet splits (A-F, G-P, Q-Z) are worker
allocation boundaries, not type boundaries. All DICT pages use the same
extraction prompt. Adding sub-types for worker allocation adds complexity
without improving extraction quality.

**Alternative C: 6 types (merge CATEGORIES into RULES, remove TOC as separate type)**

Rejected because: CATEGORIES pages (47-66) have a fundamentally different
structure from RULES pages. Category pages contain numbered lists with
descriptions and comma-separated examples. Rule pages contain bold rule
statements with STE/non-STE example pairs. Merging them forces the extraction
prompt to handle both structures, which doubles the prompt complexity
and increases the risk of missed content.

### Why Pages 43-66 Are Combined as RULES+CAT

Pages 43-66 present a structural overlap that is part of the spec design:

- Pages 43-46 contain rules only (Rule 1.1 through Rule 1.4).
- Pages 47-66 contain both rules AND technical noun categories.
  The categories are part of Rule 1.5 (technical names) and Rule 1.6
  (technical verbs), but they use a different layout from other rules.

The spec interleaves these two content types intentionally.
Keeping them as a combined range with clear classification rules
is better than three alternatives:

1. **Split at page 47**: Workers assigned to pages 43-46 get RULES type.
   Workers assigned to pages 47-66 get CATEGORIES type. This omits
   Rules 1.5 and 1.6 from the RULES extraction.

2. **Split at page 67**: Workers assigned to pages 43-66 get RULES type.
   The category content on pages 47-66 is extracted as rules.
   This omits the category structure from the CATEGORIES extraction.

3. **Duplicate extraction**: Run both RULES and CATEGORIES prompts
   on pages 43-66. This wastes compute resources on 24 pages and
   requires deduplication of shared content.

The chosen approach (RULES+CAT with classification rules) preserves
all content while avoiding duplication.

### Why the Quick Lookup Table Combines Types for Workers

The Quick Lookup table at the end of this document assigns worker batches.
Some batches combine section types (for example, RULES+CAT for W011-W016).
This is done to:

- Keep worker page counts balanced (6 pages per batch maximum).
- Avoid splitting a logical unit (a rule with its categories) across workers.
- Reduce the total number of worker launches (109 instead of 120+).
