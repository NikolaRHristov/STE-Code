# STE-Code Validation Protocol

## Overview

> **RAILS**: Validate every action against `references/rails.md` — 8 immutable guardrails.

Systematic validation of worker extraction output. Run after each batch (every 3 workers)
and after the full merge. Catches fabrication, truncation, and incompleteness.


> **RAILS**: Before any action, validate against .
> All 8 rails apply: stage isolation, naming, completion integrity, content fidelity,
> formatting standards, factual correctness, progress tracking, error recovery.

### Integration with Extraction Workflow

This validation protocol integrates with the extraction orchestrator defined in
`skills/extraction/SKILL.md`. The extraction skill launches 109 parallel
`hermes -z` workers in 37 batches of 3. After each batch completes, run the
per-batch checks (Checks 1–4 below) before launching the next batch. If a check
fails, apply the recovery protocol in this document before the extraction skill's
fallback of "split the page range in half." The extraction skill's quality checks
(>3KB, >30 lines, no mid-word truncation) align with the thresholds here.

**Workflow sequence:**

1. Extraction skill launches batch N (3 workers).
2. Extraction skill waits for batch completion.
3. Validation skill runs Checks 1–4 on batch N output.
4. If all checks pass: proceed to batch N+1.
5. If any check fails: apply Recovery Protocol (below), then re-extract.
6. After all 37 batches: run Full-Extraction Validation.

## Per-Batch Validation (After Every 3 Workers)

Run after launching and waiting for each batch of 3 workers.

### Check 1: File Existence and Size

```bash
for w in w007 w008 w009; do
  f="ste-code/extracted/${w}-p*.md"
  if [ -f "$f" ]; then
    lines=$(wc -l < "$f")
    bytes=$(wc -c < "$f")
    if [ "$lines" -lt 30 ]; then
      echo "FAIL $w: only $lines lines — possible truncation or empty extraction"
    elif [ "$lines" -lt 80 ]; then
      echo "WARN $w: $lines lines — may be light content (check manually)"
    else
      echo "PASS $w: $lines lines, $bytes bytes"
    fi
  else
    echo "FAIL $w: file not found — worker did not produce output"
  fi
done
```

### Check 2: Content Signals

Verify the file contains expected markers for its page range:

| Page Range | Expected Content Signal |
|------------|------------------------|
| 1-12 | "Copyright", "Highlights", "ASD-STE100 Simplified Technical English" |
| 13-66 | "Section 1", "Rule 1.", "Part 1" |
| 67-128 | "Section 4", "Section 5", "Rule 5.", "WARNING" |
| 129-360 | "Part 2", "Dictionary", "Word", "APPROVED", "UNAPPROVED" |
| 361-434 | "Appendix", "Index", "Issue", "Change" |

```bash
# Example: check a dictionary-range worker
grep -c "APPROVED\|UNAPPROVED" ste-code/extracted/wNNN-p*.md
# Should be >5 for dictionary pages
```

### Check 3: Truncation Detection

The most common failure mode: worker context fills up and output is cut mid-sentence.

```bash
# Last 3 lines of output should end cleanly (period, page footer, or table row)
tail -3 ste-code/extracted/wNNN-p*.md
```

Red flags:
- Last line ends mid-word ("The procedure for remo")
- Last line is a partial table row
- No page footer on last page ("2025-01-15", "Issue 9", "Page NNN")

If truncated, split the worker's page range in half and re-extract both halves.

### Check 4: Fabrication Detection

Fabricated output shows these patterns:
- Modern software examples in spec extraction ("React", "Docker" in page content)
- Commentary language ("This page describes...", "The key point is...")
- Missing spec boilerplate (no "ASD-STE100 Simplified Technical English" header)
- Smooth, flowing prose instead of spec's terse rule format

If fabrication suspected, compare against original page:
```bash
diff <(head -20 spec/issue-09-2025/page-NNNN.md) <(head -20 ste-code/extracted/wNNN-p*.md)
```

### Edge Case Handling

#### Full Batch Failure

If all 3 workers in a batch produce empty output or no output files:

1. Check that the `spec/issue-09-2025/` directory exists and is readable.
2. Check that `ste-code/extracted/` exists and is writable.
3. Check that the `hermes` binary is available and the model (`deepseek-v4-pro`) responds.
4. If the infrastructure is healthy, cut the page range per worker from 4 pages to
   2 pages and re-launch the batch with 6 workers instead of 3.
5. If even 2-page workers fail, the spec source files may be corrupt. Run a
   manual read of one page to confirm.

#### Timeout During Validation

If a `grep`, `wc`, or `diff` command in Checks 1–4 hangs or times out:

1. Kill the hung command.
2. The file under check is likely corrupt (binary data, encoding error, or
   malformed markdown). Remove it.
3. Mark the worker as FAIL and re-extract with the page range split in half.

#### File System Errors

If the output directory runs out of disk space, or a file cannot be written:

1. Check available disk space with `df -h ste-code/extracted/`.
2. Remove stale or duplicate extraction files from failed previous runs.
3. If space is sufficient but writes fail, check file permissions with
   `ls -la ste-code/extracted/`.
4. Re-launch the failed batch after the file system issue is resolved.

### Recovery Protocol

Use this protocol when a validation check fails. The protocol gives clear
actions for each failure type. Always try these actions before the extraction
skill's fallback of "split the page range in half."

#### Truncation Confirmed

If Check 3 confirms truncation (last line is mid-word, partial table, or
missing page footer):

- Split the original 4-page range into two 2-page ranges.
- Launch two new workers, one for each 2-page range.
- Validate each new output with Checks 1–4.
- If truncation recurs on a 2-page range, split to 1 page per worker.

#### Fabrication Confirmed

If Check 4 and the `diff` command confirm fabrication (content does not match
the source page):

1. Remove the fabricated output file immediately.
2. Launch a new worker with an explicit anti-fabrication instruction appended to
   the prompt:
   ```
   Do not paraphrase. Do not add commentary. Copy the source text exactly.
   Output verbatim markdown, character for character.
   ```
3. If the re-extraction still produces fabricated output, flag the page range
   for manual extraction. Add an entry to `ste-code/validation-log.md`:
   ```
   ## Manual Extraction Required: Worker wNNN (pages X–Y)
   - Reason: Repeated fabrication after 2 re-extraction attempts
   - Pages: X, X+1, X+2, X+3
   - Date: YYYY-MM-DD
   - Action: Extract these pages by hand or with a copy-paste tool
   ```

#### Output Present but Wrong Content

If a worker produced a file of reasonable size (>30 lines) but the content is
from the wrong page range, or is scrambled, or is a duplicate of another
worker's output:

1. Compare the first 5 lines against the expected source page:
   ```bash
   head -5 ste-code/extracted/wNNN-p*.md
   head -5 spec/issue-09-2025/page-XXXX.md
   ```
2. If the content is from a different page range, the worker read the wrong
   source files. Re-launch with the page range made explicit in the file name.
3. If the content is scrambled (lines out of order, mixed pages), the model
   lost context mid-extraction. Split to 2-page ranges and re-extract.
4. If the content is a near-duplicate of another worker's output, check that
   the two workers did not overlap in page range. If they overlapped, re-launch
   with non-overlapping ranges.

### Threshold Rationale

The validation thresholds use these values for the reasons below:

| Threshold | Value | Rationale |
|-----------|-------|-----------|
| FAIL line count | < 30 lines | A 4-page extraction produces 4 pages × ~25 lines/page = ~100 lines minimum. One page alone is ~25 lines. Below 30 lines means either fewer than 2 pages were read, or the output is empty except for a header. This is a clear failure. |
| WARN line count | 30–79 lines | 30 lines could be a single page; 80 lines is the lower bound for 2+ full pages of content. This range may mean the worker read only part of its 4-page assignment. A manual check is needed. |
| PASS line count | ≥ 80 lines | 80+ lines is the minimum expected from 3–4 pages of spec text. Most workers produce 100–200 lines. |
| Content signal match | > 5 hits | Dictionary pages (Part 2) have many APPROVED/UNAPPROVED entries. Fewer than 5 hits on a dictionary-range worker means the worker missed most of the content or read the wrong section. |
| Total extraction size | > 500 KB | 434 pages at ~1.2–1.5 KB/page of plain markdown text yields ~520–650 KB. Below 500 KB means pages were skipped or content was stripped. |
| Dictionary entries | > 2000 | The dictionary has 875 approved words plus ~1,400 unapproved words with usage examples. Below 2,000 entries means large parts of the dictionary are missing. |

These thresholds derive from the known structure of the ASD-STE100 Issue 9 spec
(434 pages, ~25 lines/page, 4 pages/worker, 109 workers). If the spec source
changes (different issue, different page count), adjust thresholds accordingly.

## Spot-Check Protocol

For every 10th batch (every 30 workers), run a manual spot-check:

1. Pick a worker's output file at random
2. Pick a page number from that worker's range
3. Read the original spec page directly
4. Compare first 50 lines of worker output vs spec page
5. Check for: exact text match, no paraphrasing, no omission, no fabrication

Record results in `ste-code/validation-log.md`:

```
## Spot-Check: Batch 10 (W028-W030)
- Worker: w028
- Page checked: 111
- Result: PASS — exact match, all 4 pages preserved
- Notes: None
```

## Known Limitations

The validation checks in this protocol have these known limits:

- **Content signal check (Check 2):** The `grep`-based signal check can produce
  false negatives if page headers use variant formatting (for example, "Section
  One" instead of "Section 1", or "APPROVED:" with a colon instead of
  "APPROVED" alone). Always verify a FAIL from Check 2 with a manual read of
  the first 10 lines before re-extraction.

- **Fabrication detection (Check 4):** The pattern-based detection catches
  obvious fabrication (modern software terms, commentary language) but cannot
  catch subtle paraphrasing where a model rewrites spec text in its own words
  while keeping the same meaning. Only a manual spot-check or a diff against
  the source page can catch subtle paraphrasing.

- **Truncation detection (Check 3):** The last-line check assumes the last page
  ends with a footer. If a worker extracts the full last page but the source
  page has no footer, the check may report a false FAIL. Always confirm by
  reading the last 10 lines manually.

- **Threshold specificity:** The 30-line FAIL and 80-line WARN thresholds apply
  to the ASD-STE100 Issue 9 spec at ~25 lines/page. If the source changes
  (different spec, different page density, different page count), the thresholds
  must be recalibrated.

- **Single-pass validation:** Each batch is validated exactly once. If a
  transient error (network blip, model overload) causes a false FAIL on a
  re-extraction, the protocol does not have a retry loop. Add manual retries
  for suspected transient failures.

- **Dictionary completeness (Content Volume):** The >2,000 entry threshold is a
  coarse check. It cannot detect if a specific word is missing from the
  dictionary. Use a per-word audit for strict completeness checks.
