## RAIL 1: Stage Isolation

**Rule**: A process in Stage N MUST NOT write to Stage N+1 or Stage N-1 directories.

| Stage | Directory | Allowed Actions |
|-------|-----------|-----------------|
| 1 — Extract | `extracted/` | Write `w*-p*.md`. Read `spec/issue-09-2025/`. |
| 2 — Refine | `refined/` | Read `extracted/`, write `r*-p*.md`. |
| 3 — Merge | `merged/` | Read `refined/` (or `extracted/`), write to `merged/`. |
| 4 — Adapt | `adapted/` | Read `merged/`, write to `adapted/`. |
| 5 — Artifacts | `artifacts/` | Read `adapted/`, write `.txt` files. |

**Violation**: Writing adaptation files while extraction is in Stage 1.
**Violation**: Placing files in `ste-code/` root instead of a stage directory.
**Violation**: Reading from `extracted/` when `refined/` is available (Stage 3+).

**Quality Gate**: 0 files in the wrong stage directory. Run `find <stage-dir> -name '*.md'` and confirm every filename matches the stage prefix for that directory. Allowed violations: ≤0.

**Violation**: `coding-rules-part1-sec1.md` (wrong stage, wrong naming).

**Rule**: NEVER claim a batch, stage, or phase complete without verification.

**Before claiming "Batch N complete":**
- [ ] All 3 output files exist on disk
- [ ] Each file > 3KB (>30 lines)
- [ ] Last 3 lines end cleanly (no mid-word truncation)
- [ ] Update PROGRESS.md with [x]

**Before claiming "Stage complete":**
- [ ] All files for that stage exist (e.g., 109/109 for extraction)

**Violation**: PLAN.md claiming "CORE ARTIFACTS COMPLETE ✅" when 288 pages unread.
**Violation**: PROGRESS.md showing [x] for a batch whose files don't exist.

**Quality Gate (Batch)**: file_count = 3, min_lines ≥ 30 per file, truncation_count = 0. All three must pass or the batch is not complete.
**Quality Gate (Stage)**: file_count = expected_total (e.g., 109), coverage_pages = 434, spot_check_pass = 3/3. All three must pass or the stage is not complete.

## RAIL 4: Content Fidelity

**Rule**: NEVER fabricate, summarize, or adapt content that isn't backed by source data.

**Extraction workers**: Output EXACT spec text. Never:
- Add commentary ("This page describes...")
- Add modern terms not in the spec
- Summarize instead of extracting fully

**Refinement workers**: Reformat only. Never:
- Delete any word, number, or example
- Merge different examples into one
- Change rule numbers or section structure

**Adaptation workers**: Ground every claim. Never:
- Write an adapted rule without referencing the original rule from master.md
- Invent synonyms not in the original synonym table
- Claim a category count without verifying against master.md

**Fabrication detection signals** (if output contains any of these, it's fabricated):
- Modern software terms in spec extraction: "React", "Docker", "npm", "async/await"
- Commentary language: "This page describes", "The key point is", "In summary"
- Missing spec boilerplate: no "ASD-STE100" header
- Wrong facts: "22 categories", "deepseek-pro normalizes to flash", "hermes -z doesn't support file I/O"

**Quality Gate**: 0 fabrication signals detected. Run `grep -c -E 'React|Docker|npm|async/await|This page describes|The key point is|In summary' <file>` — must return 0. For adaptation files, additionally confirm every adapted rule cites an original rule from master.md.

## RAIL 5: Formatting Standards

**Rule**: All markdown output MUST follow these rules.

### Headings
```
✅ # Page N of M          ← Every file starts with this
✅ ## Section Title        ← Major sections
✅ ### Rule X.Y            ← Rule headings
✅ #### WORD (POS)         ← Dictionary entries (refined format)

❌ ### ASD-STE100          ← Proper names are not headings
❌ ### Heading\nText       ← NEVER glue heading to text
```

### Spacing
```
✅ ### Heading            ← Heading
✅                        ← BLANK LINE (mandatory)
✅ Content starts here    ← Content

❌ ### Heading            ← Heading
❌ Content starts here    ← NO blank line = GLUED
```

### Tables
```
✅ | Header | Header |    ← Header row
✅ |--------|--------|    ← Separator row  
✅ | Cell   | Cell   |    ← Data rows
✅                        ← BLANK LINE after table

❌ | Cell |\nNext text     ← No blank line after table
```

### STE/Non-STE Examples
```
✅ > **STE:** [example text]
✅ > **Non-STE:** [example text]

❌ STE: [text]             ← Must use blockquote + bold label
❌ Non-STE: [text] on same line as STE
```

### Dictionary Entries (refined format)
```
✅ #### WORD (POS) — APPROVED
✅ - **Meaning:** [text]
✅ - **Forms:** [form1, form2]
✅ - **STE:** [example]
✅ - **Non-STE:** [example]

❌ Word | Meaning merged in one column  ← Raw extraction format, not refined
```

**Quality Gates**:
- Glued headings: `grep -cP '^#{1,4} [^\n]+\n[^ \n#]' <file>` must return 0. Allowed: ≤0.
- Missing blank lines after tables: `grep -cP '^\|.*\|\n[^\n|]' <file>` must return 0. Allowed: ≤0.
- Triple blank lines: `grep -cP '\n\n\n\n' <file>` must return 0. Allowed: ≤0.
- STE/Non-STE format: no bare `STE:` or `Non-STE:` outside blockquotes. Allowed: ≤0.

## Known Limitations

### Glued-Heading Detection

The `grep` command for detecting glued headings (`grep -cP '^#{1,4} [^\n]+\n[^ \n#]'`) has these known limitations:

- **PCRE requirement**: The `-P` flag needs GNU grep or a PCRE-aware grep implementation. On systems without PCRE support, use `grep -E` with a less precise pattern or a dedicated linter script.
- **False positives**: A heading followed by a code block that starts on the next line (e.g., ` ``` `) may be flagged as glued even when the blank line is present inside a fenced block. This is rare but possible.
- **False negatives**: The regex only detects headings immediately followed by non-blank, non-heading content. If a heading is followed by an empty line that contains invisible whitespace characters (e.g., trailing spaces), the check passes but the rendering may still appear glued visually.
- **Multi-byte characters**: Headings containing Unicode characters may not match correctly on all grep implementations.

### 30-Line Threshold (Rail 3)

The >30-line minimum for extraction files assumes a 4-page extraction batch. For smaller batches (e.g., 2-page extractions), 30 lines may be too high. For larger batches, it may be too low. Adjust the threshold proportionally:

| Pages extracted | Minimum lines |
|-----------------|---------------|
| 2 pages | >15 lines |
| 4 pages | >30 lines |
| 8 pages | >60 lines |

### Factual Correctness Drift (Rail 6)

The facts in Rail 6 are hardcoded. If the project model, rule count, stage names, or category count changes and Rail 6 is not updated, false-positive fabrication flags can occur. The meta-instruction in Rail 6 addresses this, but it depends on manual discipline. An automated audit script that diffs Rail 6 against live project constants is the preferred long-term solution.

### Stage Isolation (Rail 1) — Cross-Stage Reads

Rail 1 allows Stage 3 (Merge) to read from `extracted/` as a fallback when `refined/` is unavailable. This is intentional but creates a subtle edge case: if `refined/` exists but is incomplete (e.g., 107 of 109 files), the merge worker may silently read the remaining 2 from `extracted/` and produce a merged output that mixes refined and unrefined content. Audit merged files for format consistency when this fallback path is used.

## Relationship to Worker Rails

The file `worker-rails.md` (at `.agents/references/worker-rails.md`) defines 10 worker-level rails (W1–W10) that are a subset and specialization of these process rails. The mapping is:

| Process Rail | Worker Rails | Relationship |
|-------------|-------------|--------------|
| RAIL 2 (Naming Convention) | W10 (Naming Correct) | Direct subset — W10 enforces the naming pattern at the individual worker level |
| RAIL 4 (Content Fidelity) | W3 (No Fabrication), W4 (Boilerplate Control), W9 (Content Complete) | Decomposition — the single process rule splits into three self-check prompts for workers |
| RAIL 5 (Formatting Standards) | W1 (Page Header), W2 (No Glued Headings), W5 (STE/Non-STE Format), W6 (Tables Clean), W7 (Blank Line After Tables), W8 (No Triple Blanks) | Decomposition — the five formatting sub-rules map to six self-check items |

Worker rails are designed to be appended to every worker prompt as an inline self-validation checklist. Process rails are the authoritative source — worker rails derive from them. When a process rail changes (e.g., a new naming pattern, a new fabrication signal), update the corresponding worker rail(s) at the same time to keep them in sync.

Rails without a worker-level equivalent (RAIL 1 Stage Isolation, RAIL 3 Completion Integrity, RAIL 6 Factual Correctness, RAIL 7 Progress Tracking, RAIL 8 Error Recovery) are enforced at the orchestrator level, not by individual workers.
