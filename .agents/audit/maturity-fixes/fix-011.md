# Refinement Protocol — 9 Rules (Full Protocol)

Reformat extracted spec files into clean, standardized markdown. Zero content loss — format only. Agent-agnostic.

## When to Use
- After extraction phase complete (all 109 raw files exist)
- When extracted tables show PDF 4-column interleaving artifacts
- When heading hierarchy is inconsistent
- When STE/non-STE examples are not clearly delineated
- Before adaptation phase (clean input = better adaptation)

## What This Fixes

| Problem in Raw Extraction | Refined Output |
|---------------------------|----------------|
| STE examples merged with non-STE in dictionary tables | `**STE:**` / `**Non-STE:**` line separation |
| 4-column PDF interleaving in dictionary entries | Clean 2-column layout |
| `###` used for proper names ("ASD-STE100") | `**bold**` for names, `###` only for real headings |
| Page headers repeated | Collapsed to once per section |
| Rule examples inconsistent | Standardized blockquote format |
| Page footers ("Issue 9", "2025-01-15") | Single page metadata line |
| Missing or inconsistent code blocks | Fenced with language identifier |
| Tables without headers | Headers added where detectable |
| Lists with inconsistent indentation | Standardized 2-space indent |

## Rationale: Why 9 Rules

The 9 rules each target a distinct, recurring class of PDF-to-text extraction artifact. No rule is cosmetic — each prevents a downstream failure.

| Rule | Problem Class | Downstream Risk if Skipped |
|------|--------------|---------------------------|
| Rule 1: Zero Content Loss | Incomplete extraction | Adaptation phase produces wrong rules |
| Rule 2: Standardized Headings | Ambiguous hierarchy | Auditor cannot cross-reference rules |
| Rule 3: Table Formatting | Unparseable tabular data | Dictionary entries fail populator agent |
| Rule 4: STE/non-STE Format | Merged examples | Adaptation phase cannot distinguish compliance |
| Rule 5: Code Blocks | Misrendered fences | Linters reject as invalid markdown |
| Rule 6: Dictionary Format | Inconsistent entries | SCE Populator agent produces malformed output |
| Rule 7: Page Metadata | Missing source trace | Auditor cannot verify claims against source |
| Rule 8: List Standardization | Parser confusion | Downstream tools misparse multi-level lists |
| Rule 9: Consistent Spacing | Unpredictable diffs | Git diffs become noisy, auditor false-positives |

Each rule is non-negotiable because the pipeline stages are sequential — a defect at refinement stage propagates to merge, adaptation, and artifacts. Fixing a refinement defect at adaptation stage costs 5-10x the effort.

The rule count stayed at 9 because each addresses a semantically distinct concern. Combining rules (e.g., merging spacing into heading rules) would create ambiguous instructions. Splitting rules (e.g., separate rules for opening spacing vs closing spacing) would bloat the protocol without adding decision power.

## 9 Refinement Rules (NON-NEGOTIABLE)

### Rule 1: ZERO CONTENT LOSS
Every word, number, example, table cell from the original extraction MUST appear in the refined output. Format only — never delete.

### Rule 2: STANDARDIZED HEADINGS
```
# Page N of M          ← Every file starts with this
## Section Title        ← Major sections (Section 1, Part 2, etc.)
### Rule X.Y            ← Rule headings
#### WORD (POS)         ← Dictionary entries
```

### Rule 3: TABLE FORMATTING
Clean markdown with header row + separator row:
```
| Header 1 | Header 2 | Header 3 |
|----------|----------|----------|
| Cell 1   | Cell 2   | Cell 3   |
```
Align columns. Escape pipe chars with `\|`. Merge split cells.

### Rule 4: STE/NON-STE EXAMPLE FORMAT
```
> **STE:** [The STE-compliant example text, fully written]
> **Non-STE:** [The non-compliant example text, fully written]
```
Separated by blank line. Never merge STE/non-STE into same line.

### Rule 5: CODE BLOCKS
Fenced with language identifier. Never bare ```.

### Rule 6: DICTIONARY ENTRY FORMAT
```
#### WORD (POS) — APPROVED
- **Meaning:** [exact approved meaning]
- **Forms:** [form1, form2, form3]
- **STE:** [example]
- **Non-STE:** [example]

#### word (POS) — UNAPPROVED
- **Alternatives:** [alternative1 (POS), alternative2 (POS)]
- **STE:** [example using alternative]
- **Non-STE:** [example using unapproved word]
```

### Rule 7: PAGE METADATA
```
# Page NNN of 434

> **Source:** ASD-STE100 Issue 9, January 2025
> **Pages:** NN–MM of 434
```
Remove repetitive "ASD-STE100 Simplified Technical English" headers from body.

### Rule 8: LIST STANDARDIZATION
- Numbered: `1. `, `2. ` (not `1)` or `1-`)
- Bullets: `- ` (not `* ` or `• `)
- Nested: 2-space indent

### Rule 9: CONSISTENT SPACING
- `### Heading` → blank line → content
- Content end → blank line → next heading
- Table end → blank line → next content
- Exactly one blank line between sections (never two, never zero)
- No trailing whitespace
- No triple blank lines

## Edge Cases

### Corrupted or Missing Dictionary Entries

When the raw extraction contains incomplete dictionary entries (missing POS tag, missing meaning, or missing example):

1. Flag the entry with a `<!-- CORRUPTED: missing [field] -->` comment above the entry.
2. Preserve all available fields. Do not invent missing content.
3. Format available fields per Rule 6. Leave missing fields as `- **Meaning:** [MISSING]`.
4. Log the file path and entry word in the batch verification report.

If more than 3 entries in a file are corrupted, the source pages may have a PDF parsing error. Escalate to re-extraction (see Failure Recovery).

### Tables Spanning Multiple Raw Extraction Pages

When a table in the raw extraction is split across two page files (e.g., page 23 ends mid-row, page 24 continues the same table):

1. Identify the split by checking for a page boundary where a table row has no closing pipe `|`.
2. Merge the split rows into a single continuous table in the first page's refined file.
3. Add a note in the second page's refined file: `<!-- Table continues from page NN -->`.
4. Do NOT duplicate the header row in the merged table. Keep one header row at the top.

### Ambiguous STE/non-STE Boundaries

When raw extraction has examples where the compliant/non-compliant boundary is unclear:

1. Default to `> **STE:**` for the first example, `> **Non-STE:**` for the second.
2. If only one example exists and its compliance status is unclear, use `> **Example:**` without STE/non-STE label.
3. Mark with `<!-- AMBIGUOUS: compliance status unclear -->` so the auditor can review.
4. Never guess compliance status when ambiguous.

### Special Characters in Code Examples

When raw extraction contains characters that break markdown parsing (backticks inside code fences, pipe chars in table cells, angle brackets in inline code):

1. Wrap code examples with triple-backtick fences using a language identifier.
2. Escape pipe characters inside table cells with `\|`.
3. For angle brackets (`<`, `>`) that are not HTML tags, keep them as-is inside code fences. Outside code fences, use HTML entities (`&lt;`, `&gt;`).
4. For backticks that appear inside code examples, use a different fence length: ```` ````` ```` (more backticks than the content contains).

### Tables Without Detectable Headers

When a raw extraction table has no header row:

1. Check neighboring pages for a continuation of the same table that includes headers.
2. If headers are found in a neighboring page, copy them to the current table.
3. If no headers exist anywhere, add `<!-- MISSING HEADERS: table from page NN, no header row found in extraction -->` above the table.
4. Do not invent header names.

## Failure Recovery

When a verification check fails, do not proceed to the next batch. Follow the recovery path for the specific check.

### Check 1 Failure: Output line count less than input line count

Cause: Content was dropped during refinement (violation of Rule 1: Zero Content Loss).

Recovery steps:
1. Diff the input and output files to identify missing lines.
2. Re-refine the same source pages with an explicit instruction: "Do not omit any content. Every line from the input must appear in the output."
3. If the second attempt also fails, escalate to the auditor. The source pages may contain content that the model truncates due to output length limits. Split the file into 2-page chunks and refine separately.

### Check 2 Failure: Missing page numbers in output

Cause: Page metadata was stripped incorrectly (violation of Rule 7).

Recovery steps:
1. Check if the page number appears but in a non-standard location (e.g., inline text instead of heading).
2. Re-refine with explicit format for page metadata: "The output MUST start with `# Page NNN of 434`."
3. If the second attempt also fails, manually edit the heading line. This is a 30-second fix and does not need a third retry.

### Check 3 Failure: Repeated "ASD-STE100" headers in body

Cause: The worker did not collapse page headers (violation of Rule 7).

Recovery steps:
1. Manually remove duplicate headers. This is a search-and-replace operation — 5 seconds per occurrence.
2. Re-refine only if more than 10 duplicate headers exist (indicates a systematic failure in header detection).

### Check 4 Failure: STE/non-STE pairs not using `> **STE:**` format

Cause: The worker used a different example format (violation of Rule 4).

Recovery steps:
1. Re-refine the file with explicit format instruction: "ALL examples MUST use `> **STE:**` and `> **Non-STE:**` blockquote format."
2. If the second attempt fails, the source extraction may not clearly separate STE from non-STE. Mark the file as `<!-- AMBIGUOUS -->` and escalate to the auditor.

### Check 5 Failure: Tables without header rows

Cause: The raw extraction table had no detectable header row (see Edge Cases section).

Recovery steps:
1. Check neighboring page files for the same table with headers.
2. If headers exist in a neighbor, copy them manually.
3. If no headers exist anywhere in the source, add the `<!-- MISSING HEADERS -->` comment. This is an extraction defect, not a refinement defect. Escalate to re-extract the affected pages.

### Escalation Protocol

If any file fails verification twice:

1. Stop the current batch. Do not start new batches.
2. Log the file path, the failed check number, and both attempt outputs.
3. Set the batch status to `❌` in REFINE-PROGRESS.md with a note: "Escalated — batch N, file rNNN-pPPPP-PPPP.md, check #X failed twice."
4. Move to the next batch. The auditor resolves escalated files after all clean batches are complete.
