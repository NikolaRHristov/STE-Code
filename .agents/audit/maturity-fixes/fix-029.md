## Design Rationale

### Why 9 Rules

The refinement phase splits formatting into 9 discrete rules. Each rule addresses
one category of extraction artifact. This design has three benefits:

1. **Isolation.** A worker can check one rule at a time. If a rule fails, the
   failure traces to one formatting category instead of an unknown problem.
2. **Testability.** Each rule maps to a verification check in the Verification
   section. A failed check points to one rule.
3. **Extensibility.** A new formatting problem needs only one new rule. The
   other 9 rules stay unchanged.

### Why This Dictionary Entry Format

The format at Rule 6 uses `#### WORD (POS) — APPROVED` for approved entries and
`#### word (POS) — UNAPPROVED` for unapproved entries. This design comes from
the ASD-STE100 Issue 9 source layout. The source uses uppercase for approved
words and lowercase for unapproved words. The format keeps this distinction.
The `— APPROVED` / `— UNAPPROVED` suffix makes the status explicit for tools
that parse the output.

### Rejected Alternatives

| Rejected Approach | Why Rejected |
|-------------------|--------------|
| Combine STE and non-STE examples in one table row | Merged rows hide the contrast that the rule teaches |
| Use `###` for all dictionary words | The heading would match Rule headings. Search and navigation tools cannot tell rules from words. |
| Auto-generate missing table headers from context | Guessed headers introduce errors. The refinement adds headers only when the source data makes them clear. |
| Remove all page metadata (Issue number, date) | Metadata is not noise. It is provenance. The output keeps it in one block. |
| Merge refinement and extraction into one pass | Two passes let each pass focus on one job. Extraction reads PDFs. Refinement fixes formatting. Combined passes fail at both. |

## Refinement Rules (NON-NEGOTIABLE)

### Rule 1: ZERO CONTENT LOSS
Every word, every number, every example, every table cell from the original
extraction MUST appear in the refined output. Format only — never delete.

### Rule 2: STANDARDIZED HEADINGS
```
# Page N of M          ← Every file starts with this
## Section Title        ← Major sections (Section 1, Part 2, etc.)
### Rule X.Y            ← Rule headings
#### WORD (POS)         ← Dictionary entries
**STE:**                ← STE examples (bold label, not a heading)
**Non-STE:**            ← Non-STE examples (bold label, not a heading)
```

### Rule 3: TABLE FORMATTING
All tables MUST use clean markdown:
```markdown
| Header 1 | Header 2 | Header 3 |
|----------|----------|----------|
| Cell 1   | Cell 2   | Cell 3   |
```
- Align columns consistently
- Escape pipe characters inside cells: `\|`
- Merge split cells where the PDF layout broke them

### Rule 4: STE/NON-STE EXAMPLE FORMAT
All example pairs MUST use this exact format:
```markdown
> **STE:** [The STE-compliant example text]

> **Non-STE:** [The non-compliant example text]
```
Never merge STE and non-STE into the same line or paragraph.

### Rule 5: CODE BLOCKS
Any code-like content (pipeline steps, shell commands, Python snippets) in
``` fenced code blocks with language identifier.

### Rule 6: DICTIONARY ENTRY FORMAT
Each dictionary entry MUST be:
```markdown
#### WORD (POS) — APPROVED
- **Meaning:** [exact approved meaning]
- **Forms:** [form1, form2, form3]
- **STE:** [example]
- **Non-STE:** [example]

#### word (POS) — UNAPPROVED
- **Alternatives:** [alternative1 (POS), alternative2 (POS)]
- **STE:** [example using alternative]
- **Non-STE:** [example using unapproved word]
```

### Rule 7: PAGE METADATA
Remove repetitive page headers ("ASD-STE100 Simplified Technical English" on
every page). Replace with a single metadata block at file start:
7. METADATA: Add page header FIRST, then metadata block below it:
   # Page NNN of 434
   
   > **Source:** ASD-STE100 Issue 9, January 2025
   > **Pages:** NN–MM of 434
   
   Remove repetitive "ASD-STE100 Simplified Technical English" headers from body text.
```

### Rule 8: LIST STANDARDIZATION
- Numbered steps: `1. `, `2. ` (not `1)` or `1-`)
- Bullet lists: `- ` (not `* ` or `• `)
- Nested lists: 2-space indent
- Multi-paragraph list items: 2-space indent on continuation lines

### Rule 9: CONSISTENT SPACING — HEADINGS, PARAGRAPHS, TABLES

**CRITICAL: Never glue headings to text. Always separate with blank lines.**

```
❌ WRONG:
### Rule 1.1
Rule text starts immediately...

❌ WRONG:
| Header |
|--------|
| Cell |

✅ CORRECT:
### Rule 1.1

Rule text on its own line, separated by a blank line from the heading above.

| Header |
|--------|
| Cell |

Next paragraph separated by a blank line from the table above.
```

**Spacing rules (non-negotiable):**
- `### Heading` → blank line → content (paragraph, table, list, or blockquote)
- Content end → blank line → next `### Heading`
- Table end → blank line → next paragraph or heading
- List end → blank line → next paragraph or heading
- Blockquote end → blank line → next content
- Exactly one blank line between sections (never two, never zero)
- No trailing whitespace on any line
- No triple blank lines anywhere

## Edge Case Handling

### Content Loss on Verification

The verification step checks: output file line count >= input file line count.
When this check fails, the refined output has fewer lines than the input. This
indicates content was removed instead of reformatted.

**Recovery procedure:**

1. Mark the worker as `FAILED` in `ste-code/REFINE-PROGRESS.md`.
2. Compare the input and output files line by line. Use:
   ```
   diff ste-code/extracted/wNNN-pPPPP-PPPP.md ste-code/refined/rNNN-pPPPP-PPPP.md
   ```
3. Identify which lines were removed. Common causes:
   - A table row was dropped during 4-column reconstruction (see below).
   - A page header or footer was removed without moving its content to the
     metadata block.
   - An example pair was merged into one line.
4. Restore the lost content to the refined file.
5. Re-run the verification checks on the restored file.
6. If the same worker fails again, flag the file for manual review and continue
   with the next batch.

### Unreconstructable Tables

The 4-column PDF interleaving occurs when a 2-column dictionary table spans a
page break. The PDF extractor reads the left column of page N, then the right
column of page N, then the left column of page N+1, then the right column of
page N+1. This produces a 4-column artifact:

```
| Word A (page N, left) | Meaning A (page N, right) | Word B (page N+1, left) | Meaning B (page N+1, right) |
```

Most cases reconstruct cleanly. The worker reads the four cells and pairs the
first with the second, the third with the fourth.

**When reconstruction is impossible:**

- Merged cells that span multiple rows in the original PDF produce misaligned
  columns after extraction. The worker cannot guess the original row span.
- Tables with 3 or more original columns (rare in ASD-STE100) produce complex
  interleaving patterns.
- Dictionary entries split mid-word at a page boundary need the two fragments
  reattached. The worker does not have context from adjacent pages.

**Procedure for unreconstructable tables:**

1. The worker wraps the affected table in a comment block:
   ```markdown
   <!-- UNRECONSTRUCTABLE-TABLE-START -->
   | Col1 | Col2 | Col3 | Col4 |
   |------|------|------|------|
   | ...raw 4-column data... |
   <!-- UNRECONSTRUCTABLE-TABLE-END -->
   ```
2. The worker adds a `TODO` note above the block:
   ```markdown
   > **TODO:** This table could not be reconstructed from 4-column interleaving.
   > Manual review required. See `ste-code/review-queue.md`.
   ```
3. The verification step counts these blocks but does not fail the batch.
4. Flagged files go to `ste-code/review-queue.md` for manual reattachment.

### Page-Boundary Dictionary Entries

When a dictionary entry splits across a page boundary, the word appears on page
N and the meaning appears on page N+1. Since each worker processes 4 pages, most
splits fall inside one worker's scope. For splits at worker boundaries (page
multiples of 4), the two fragments land in different worker outputs.

**Recovery:** The merge phase (after refinement) detects partial entries and
reattaches them. The refinement phase does not need to handle this case.

## Known Limitations

| Limitation | Impact | Mitigation |
|------------|--------|------------|
| 4-column interleaving recovery has ~95% accuracy. Complex tables with merged cells may need manual fixes. | About 1 in 20 dictionary tables keeps the raw 4-column layout. | Flagged with `UNRECONSTRUCTABLE-TABLE` comments. Queued for manual review. |
| Page range boundaries that split dictionary entries mid-word need reattachment in the merge phase. | Partial entries at worker boundaries (pages 4, 8, 12, etc.) appear as fragments. | The merge phase detects and reattaches fragments. Not a refinement concern. |
| Bold detection in source text is lossy. The PDF extractor cannot always tell `**bold**` from regular text. | Some ASD-STE100 proper names may not get bold formatting. | The worker adds bold only when the source clearly marks it. |
| The refinement does not validate factual correctness of STE rules or dictionary meanings. | Formatting errors are fixed. Content errors from the source PDF persist. | The auditor agent (Agent #3) validates factual correctness in a later stage. |
| Tables with 3+ original columns are rare in ASD-STE100 but not handled by the 4-to-2-column reconstruction logic. | These tables stay in raw format. | Flagged for manual review. |
| The refinement assumes English text. Non-Latin characters in code examples may produce encoding artifacts. | Rare. ASD-STE100 is English-only. | None needed for the current source. |

The 9 refinement rules are versioned. New patterns found during refinement runs

### How to Add Rule 10 (or Higher)

When a worker finds a new formatting pattern that does not fit any of the 9
rules, follow this procedure:

1. **Document the pattern.** Write the problem description and the desired output
   format in `ste-code/refine-patterns.md`. Include:
   - The input file where the pattern was found (worker number, page range)
   - The raw extracted text that shows the pattern
   - The desired refined output
   - Why none of Rules 1-9 handle it

2. **Test on 3 samples.** Apply the proposed rule to at least 3 different pages
   that show the pattern. Confirm the rule produces correct output on all 3.

3. **Propose the new rule.** Add the proposed rule text to this section as a
   draft. Do not yet add it to the numbered rules above.

4. **Run a trial batch.** Launch one batch (3 workers) with the proposed rule
   added to the worker prompt template. Verify the output.

5. **Promote the rule.** After a successful trial batch, move the rule from the
   draft section to the numbered rules section. Increment the version number.
   Update the worker prompt template. Update the verification checks.
