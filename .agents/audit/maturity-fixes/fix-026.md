## Edge Case Handling

> **NOTE**: The recovery actions below extend Rail 8. Follow them when a worker fails.

### Worker Stops Responding (Hang)

A worker may stop mid-extraction. It writes no output and does not exit.
The `hermes -z` process stays alive but produces no progress.

**Symptoms**: Output file is missing or 0 bytes after 120 seconds.
The worker process still runs but consumes no CPU.

**Recovery**:
1. Stop the hung worker process: `kill <PID>`
2. Mark the worker as `[!]` in PROGRESS.md (not `[x]`, not `[ ]`)
3. Launch a replacement worker with the same page range
4. Check the replacement output against quality checks before marking `[x]`

### Worker Exceeds Time Limit (Timeout)

A worker may use too much time on a page range.
This occurs when pages contain dense tables or many dictionary entries.

**Recovery**:
1. Set a 300-second time limit per worker (do `timeout 300 hermes -z ...`)
2. If a worker exceeds the time limit, split its page range into two workers of 2 pages each
3. Launch both replacement workers in the next batch
4. Remove the original worker's incomplete output file

### Output Is a Directory, Not a File

A worker may make a directory at the output path instead of a file.
This occurs when the worker prompt includes a trailing `/` or misreads the path.

**Symptoms**: `ls -l ste-code/extracted/w042-p165-168.md` shows a directory.

**Recovery**:
1. Remove the directory: `rm -rf ste-code/extracted/w042-p165-168.md`
2. Fix the worker prompt to use the correct file path (no trailing `/`)
3. Launch a replacement worker with the corrected prompt
4. Mark progress only after the replacement file passes quality checks

### Broken Markdown Output

A worker may write output with broken formatting.
This occurs when page content confuses the model's markdown parser.

**Symptoms**:
- Mangled table borders: `| col1 | col2` (missing closing pipe)
- Merged dictionary entries: two words in one heading
- Missing section breaks: content from two sections glued together

**Recovery**:
1. Run the markdown lint check: count pipe characters per table row
2. If a table row has a wrong pipe count, re-extract that page range with a clearer prompt
3. Add to the prompt: "Keep table pipe characters balanced. One blank line after each table."
4. Mark the file as `[!]` until the replacement passes

### Git Commit Failure

The `git gcommit-hermes` command may fail if the working tree is dirty
from an unrelated change or if a merge conflict exists.

**Symptoms**: `git gcommit-hermes` exits with a non-zero code.

**Recovery**:
1. Run `git status` to find the cause
2. If unrelated files are dirty, stash them: `git stash`
3. Do the batch commit: `git gcommit-hermes "Batch N complete"`
4. Restore stashed changes: `git stash pop`
5. If a merge conflict exists, resolve it before the next batch

### All Three Workers in a Batch Fail

When all 3 workers in a batch fail, the batch produces no output.

**Recovery**:
1. Check the system state: disk space, API rate limits, model availability
2. Wait 60 seconds before retrying (rate limit cooldown)
3. Launch the batch again with the same 3 page ranges
4. If the second attempt fails, split each 4-page range into 2-page ranges
5. Absorb the 6 replacement workers across the next 2 batches

## Design Rationale: Batches of 3

The "batches of 3" constraint exists for these reasons:

1. **API rate limit safety**: DeepSeek enforces rate limits on concurrent requests.
   Three parallel workers stay well under typical rate limits.
   Four or more workers risk HTTP 429 (Too Many Requests) responses.

2. **Coordinator attention budget**: A human or agent coordinator must check
   6 quality gates per batch (18 checks per 3 workers).
   Four workers would need 24 checks — too many for one review cycle.

3. **Failure containment**: One failed worker in a batch of 3 wastes at most
   33% of the batch time. One failure in a batch of 5 wastes 20% but adds
   more coordination overhead to recover.

4. **Batch time predictability**: Three 4-page workers each take 20-40 seconds.
   A batch completes in 30-60 seconds wall-clock time.
   This matches the natural check-commit-loop cycle for a coordinator.

5. **Git commit granularity**: One commit per 12 pages (3 workers × 4 pages).
   This is small enough for clear blame history and large enough
   to avoid commit spam (37 commits vs 109).

**Why not 1 worker per batch?** Too slow — 109 sequential batches.
**Why not 5 workers per batch?** Rate limit risk, too many quality checks.
**Why not 10 workers per batch?** Guaranteed rate limit errors.

### Rate Limit Considerations

DeepSeek v4 Pro rate limits (typical):
- 50 requests per minute (RPM)
- 500,000 tokens per minute (TPM)

Three workers per batch use ~12,000-19,500 tokens per batch.
At 37 batches over 30 minutes, the average is ~1.2 batches per minute.
This is well under the 50 RPM limit.

Peak load: 3 concurrent requests × ~6,500 tokens = ~19,500 tokens.
This is well under the 500,000 TPM limit.

No rate limit errors are expected under normal conditions.
If rate limit errors occur, add a 120-second cooldown between batches.

## Known Limitations

1. **Dense 4-column dictionary tables**: Pages in Part 2 (Dictionary) contain
   tables with 4 columns (Word, POS, Meaning, Example).
   These tables may have broken pipe alignment after extraction.
   Manual fixes may be needed for some dictionary page outputs.

2. **Page boundary splits**: When a rule or dictionary entry spans two pages,
   the 4-page worker boundary may split the entry.
   The merge stage corrects this. Extraction workers do not handle it.

3. **Non-ASCII characters**: The spec uses phonetic symbols and special
   typographic characters (IPA, curly quotes, en dashes).
   Some models may replace these with ASCII equivalents.
   Spot-check phonetic entries after extraction.

4. **Footer/header noise**: Spec pages include running headers and page numbers.
   Workers usually strip these. Some workers may keep them.
   The refinement stage removes leftover headers and footers.

5. **Model drift**: The same prompt run twice may produce slightly different
   output (different whitespace, table alignment, or word wrapping).
   This is a property of LLM nondeterminism, not a worker bug.
   The merge stage normalizes formatting differences.

6. **Large batch queue**: 37 batches is a long-running process.
   A network interruption or machine sleep mid-run stops all progress.
   Use PROGRESS.md to resume from the last completed batch.
