# Extraction Worker Orchestration

Extract the 434-page ASD-STE100 Issue 9 spec using 109 parallel `hermes -z` workers, each processing exactly 4 pages. Coordinated in 37 batches of 3 workers. This skill is agent-agnostic — any agent can use it.

## Design Rationale

**Why 4 pages per worker?** A `hermes -z` worker with the `deepseek-v4-pro` model reliably processes 4 spec pages without truncation. Five or more pages cause mid-extraction cutoffs when tables or long rule examples fill the context window.

**Why batches of 3?** The API enforces a rate limit. Three concurrent workers stay below the limit. Sequential batches let you check output quality before you start the next batch. This prevents cascading failures across all workers.

**Why 109 workers for 434 pages?** 434 pages ÷ 4 pages per worker = 108 workers with 2 pages left over. The 109th worker processes the final 2 pages (pages 433-434). 109 workers ÷ 3 per batch = 36 full batches plus 1 final batch with 1 worker. Total: 37 batches.

## Worker Command Template

```bash
hermes -z "Read spec/issue-09-2025/page-<<START>>.md through page-<<END>>.md. 
Extract ALL content exactly into ste-code/extracted/w<<NNN>>-p<<START>>-<<END>>.md.
Do not summarize. Include every word, every table, every example.
Output ONLY the markdown file." -m deepseek-v4-pro --yolo
```

## Failure Mode Examples

These patterns show a corrupted extraction. If you see any of them, the extraction failed.

**Mid-word truncation (last line):**
```
The approved word for this context is mainten
```
The word "maintenance" is cut off. The worker stopped before it finished the sentence.

**Missing content marker:**
```
... (content continues)
```
The worker skipped content instead of extracting it. This is fabrication.

**Fabricated modern terms:**
```
Use the API endpoint to trigger the CI/CD pipeline.
```
ASD-STE100 Issue 9 does not contain terms like "API", "CI/CD", or "pipeline". These are hallucinations.

**Empty or near-empty section:**
```markdown
## Part 3 — Dictionary

(No content extracted)
```
The worker produced a header but no body. The extraction is incomplete.

**Repeated boilerplate without spec content:**
```
I have extracted pages 25-28. The content follows:
I have extracted pages 25-28. The content follows:
I have extracted pages 25-28. The content follows:
```
The worker looped on its own preamble and never reached the spec content.

## Launch Rules

- **Always** use `hermes -z "$(cat prompt.txt)" -m deepseek-v4-pro --yolo`
- **Always** launch exactly 3 workers per batch (never more)
- **Always** verify output after each batch before launching next
- **Never** use inline extraction — it defeats parallelization
- **Never** exceed 4 pages per worker (prevents truncation)
- **Always** save state: `git gcommit-hermes "Batch N complete"` after each batch

## Edge Cases

### Multi-Page Tables

When a table starts on one page and continues on the next page, the column headers often repeat on the second page. The worker must extract the table as one continuous block. If the worker splits the table at the page boundary, the output file has two incomplete tables. To detect this: look for a table that ends without a full row AND the next page starts with repeated column headers.

**Recovery:** Re-extract the page range with an extra page on each side. Example: if pages 12-15 contain a split table, extract pages 11-16 instead.

### Pages with Images or Diagrams

Some spec pages contain only an image, a diagram, or a figure with a caption. The worker must extract at minimum the figure number, the caption text, and a placeholder like `[Figure X: description from caption]`. A blank output for an image-only page is acceptable only if the page has no text content beyond the image itself.

**Recovery:** If the output is empty, check the source page. If it has a caption, re-extract with the instruction: "Include figure captions and table titles. Use [Figure N] as placeholder for images."

### Empty Appendix Pages

Some appendix pages are intentionally blank (page breaks between sections). The worker may produce an empty file or a file with only a header. This is correct behavior. Do not flag an empty file as a failure if the source page is blank.

**Check:** Open the source page. If it has no text, the empty output is valid. Mark the worker as PASS with a note "empty source page."

### Non-English Characters

The ASD-STE100 spec contains non-English example text in rule examples (French, German, and other languages used to show what NOT to write). The worker must preserve these characters exactly. Check that accented characters (é, ü, ñ, ç) and non-Latin scripts appear correctly in the output.

**Recovery:** If non-English characters are garbled (showing as `?` or mojibake), re-extract with the instruction: "Preserve all Unicode characters exactly as written. Do not transliterate."

## Quality Checks (Per Batch)

1. All 3 output files exist in `ste-code/extracted/`
2. Each file > 3KB (>30 lines)
3. Last 3 lines end cleanly (no mid-word truncation)
4. Expected keywords present (see Expected Keywords section below)
5. No fabrication signals (no "TODO", "TBD", modern software terms)
6. PROGRESS.md updated

If any check fails, re-extract with the worker's page range split in half.

## Expected Keywords

Each extracted file must contain at least one keyword from each group that applies to its page range.

**Group A — Structure (at least 2):**
`Rule`, `Section`, `Part`, `Appendix`, `FOREWORD`, `INTRODUCTION`, `Dictionary`

**Group B — Rule language (at least 1, if the page range covers rules):**
`Approved`, `Not approved`, `Keyword`, `ACRONYM`, `Part of speech`, `TECHNICAL NAME`, `TECHNICAL VERB`

**Group C — Content markers (at least 1):**
`Use`, `Do not use`, `Example`, `NOTE`, `WARNING`, `CAUTION`

**Dictionary pages only:** Group A plus these dictionary-specific terms: `Approved meaning`, `APPROVED EXAMPLE`, `NOT APPROVED`

**Appendix pages only:** Group A is sufficient. Groups B and C are optional.

If a file covers both rules and dictionary content, it must satisfy the union of the applicable groups.
