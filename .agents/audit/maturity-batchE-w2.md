- **Level:** 4
- **Summary:** Master blueprint of the 5-stage STE-Code pipeline expressed as a unified collection of Mermaid state diagrams. Covers every stage from extraction through artifacts, including gate checkpoints, data flow between stages, 3-worker batch parallelism architecture, error recovery, rails compliance, and an end-to-end unified state machine - all at command-level specificity.
- **Strengths:**
  - Exhaustive coverage: 12 sections, every pipeline stage gets its own detailed state diagram with substates
  - Executable specificity: concrete worker counts (109, 37x3), page ranges, file sizes (912KB/916KB), token counts, exact gate checks (grep commands, line counts)
  - Edge case handling: section 10 is a dedicated error state machine covering timeout, crash, hang, truncation, disk-check-before-relaunch, and fabrication detection with quarantine flow
  - Cross-references: names specific files (check-rails.py, exchange.md, PROGRESS.md, REFINE-PROGRESS.md) - all verified to exist on disk
  - Design rationale: notes explain why decisions were made (MAX 3 concurrent, never skip verification, commit only after pass, check disk before re-launching)
  - Performance considerations: parallelism architecture (section 9) explicitly documents the 3-worker concurrency model with barrier synchronization
  - Summary table (pipeline summary) provides a one-glance reference across all 5 stages
- **Gaps:**
  - No version history or changelog - no way to track when sections were added or revised
  - No meta-instructions for self-rewriting - the file describes what the pipeline IS, not how an agent should update this document when the pipeline evolves
  - No measurable quality gates as a standalone concept - gate checks are embedded in diagrams but not extracted as a reusable checklist an auditor could mechanically execute against
  - No known limitations section - for example, the 3-worker concurrency model assumes notify_on_complete reliability; no documentation of what breaks if a notification is dropped
  - No agentic-load specifications - how many tokens/context this document consumes when loaded, or guidance on which sections to load for which agent roles
- **What Level 5 Would Add:**

  - A "Known Limitations & Workarounds" section documenting: (a) notify_on_complete reliability assumptions, (b) the 3-worker limit rationale and what happens if violated, (c) git gcommit-hermes dependency, (d) hardcoded 109-worker assumption and what to change for a different-sized spec

- **Priority:** medium

### .agents/uml/error-recovery.md
- **Level:** 4
- **Summary:** Authoritative troubleshooting reference for the STE-Code pipeline covering every failure mode from worker dispatch through git push. Includes complete taxonomy of failures, per-failure recovery decision trees, audit detection methods, auto-fix vs. escalation classification, 8-process-rail and 10-worker-rail violation recovery, batch restart strategies, git disaster recovery, a unified troubleshooting state machine, and three appendices (severity classification, quick command reference, auditor trust score calculation).
- **Strengths:**
  - Exhaustive failure taxonomy (section 1): dispatch timeout, file corruption, truncation, fabrication, shell quoting errors, model normalization failure - each with detection signals and recovery paths
  - Decision trees are actionable: split strategy for truncated workers (section 2b) gives exact commands (rm, launch, merge) with verification criteria; batch restart (section 6) has a 3-tier decision tree (>90%, 50-90%, <50%) with concrete actions
  - Severity classification (Appendix A): CRITICAL/ERROR/WARNING with clear examples for each level, color-coded in diagrams
  - Self-referencing integrity: rails violations (section 5) map directly to the 8 rails from the pipeline state machine and the 10 worker rails from worker-rails.md - both cross-referenced files exist
  - Git recovery (section 7): covers commit failure, push rejection, detached HEAD, merge conflicts, and the disaster scenario of lost commits + lost files - includes reflog recovery and re-commit from disk fallback
  - Trust score model (Appendix C): quantified audit confidence with 4 tiers and thresholds, giving the auditor a measurable output
  - All cross-references verified on disk: rails.md, worker-rails.md, evidence-commands.md, worker-grid.md, execution-auditor SKILL.md, check-rails.py
- **Gaps:**
  - No version history - the document has evolved (worker rails expanded from 8 to 10, trust score added) but there's no record of when or why
  - No meta-instructions for self-rewriting - when a new failure mode is discovered in production, there's no guidance on where to insert it in the taxonomy or how to update the decision trees
  - No known limitations with workarounds section - for example: (a) the split strategy assumes a 4-page worker and splits to 2+2, but doesn't address what to do for an already-split 2-page worker that still truncates; (b) the audit auto-fix queue (AF1-AF7) is hardcoded to 7 specific fixes with no extension mechanism when a new auto-fixable pattern is discovered
  - No measurable quality gates - the trust score is calculated but there's no gate that says "trust < 0.80 blocks pipeline continuation" - the scoring and the decision are in separate sections
  - No agentic-load specifications - this is a large document (31KB, 689 lines) and there's no guidance on which sections the Extractor vs. Refiner vs. Auditor needs to load
  - Recovery commands (Appendix B) use hardcoded model name and flag (`--yolo`) rather than parameterized placeholders - if the model or flags change, the commands silently become wrong
- **What Level 5 Would Add:**
  - A version history table documenting when each failure mode was discovered and added (e.g., "shell quoting errors - discovered Batch 4, documented 2025-07-14")
  - A "How to Extend This Document" meta-section: template for adding a new failure mode (where in the taxonomy, which decision tree to update, which severity class, which recovery commands to add)
  - A "Quality Gates" section linking the trust score thresholds (1.00/0.80/0.50) to explicit pipeline continuation rules: "trust < 0.50 → HALT pipeline, full audit required; 0.50-0.79 → PAUSE, fix before next stage; 0.80-0.99 → CONTINUE with logged warnings; 1.00 → PROCEED"
  - A "Known Limitations & Workarounds" section covering: (a) single-page workers that still truncate (fallback: manual extraction), (b) auto-fix queue is closed-set (workaround: add new patterns to the auditor SKILL.md), (c) git recovery assumes reflog is intact (workaround: filesystem-based re-commit), (d) notify_on_complete unreliability under high load (workaround: timeout-based polling fallback)
  - Agentic-load specifications: total token count, per-section token counts, recommended subsets for each agent role
  - Parameterized recovery commands using `${MODEL}` and `${FLAGS}` placeholders instead of hardcoded values
- **Priority:** medium
