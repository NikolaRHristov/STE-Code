# Maturity Audit - Batch G, Worker 1

### ste-code/v2/compute/prompts/vocabulary-review.prompt.md
- **Level:** 2
- **Summary:** Parameterized prompt for extending STE-Code vocabulary with new technology/framework terms. Classifies terms into noun/verb categories, checks synonyms, assigns domain tags and severity.
- **Strengths:**
  - Clean YAML frontmatter with `loads-from` declarations listing dependency files
  - Structured 5-step classification workflow with numbered items
  - JSON output format template with all required fields
  - Variable-driven design (`domain`, `new_terms`, `organization_name`) enabling reuse
  - Output format distinguishes proposed-additions from rejected-terms with rationale
- **Gaps:**
  - `data/vocabulary/approved-nouns.json` referenced in frontmatter loads-from does not exist anywhere in the repository - the only vocabulary JSON files at that relative path are `approved-verbs.json` and `approved-adjectives.json` (and those live under `SCE/`, not `ste-code/v2/`)
  - No worked examples - the JSON output schema is shown as an empty template; a real classification example (e.g., classifying "mutex" as a noun in category X with rationale) is absent
  - No edge case handling: ambiguous terms spanning multiple categories, compound terms (e.g., "read-only"), domain-specific verbs that overlap with existing approved verbs
  - No guidance on how to resolve conflicts when a term appears in both approved and synonym lists
  - No cross-reference to the 14 core principles (P1-P14) to justify why severity is blocking vs advisory
  - No quality gate - no criterion for when a classification batch is "done" or how to validate output
  - Severity levels (`blocking / warning / advisory`) are listed but never defined - no threshold for when to assign each
- **What Level 3 Would Add:**
  - 2-3 fully worked classification examples with rationale, showing real terms going through all 5 steps
  - Concrete severity assignment rules tied to principle violations (e.g., "blocking if term violates P1 or P11")
  - Edge-case protocol for compound and ambiguous terms
  - Explicit cross-reference to `core/principles/` or the 14 core principles
  - Quality gate: after classification, verify all proposed-additions have unique terms, all have non-empty rationale, all severities align with loaded rules
  - Fix or remove the broken `approved-nouns.json` reference
- **Priority:** medium

### ste-code/v2/compute/prompts/rule-adaptation.prompt.md
- **Level:** 2
- **Summary:** Prompt for adapting STE-Code rules from a source domain to a target domain by separating invariant core from domain-specific elements and replacing vocabulary/examples.
- **Strengths:**
  - Clear conceptual model: invariant core vs domain-specific elements is explicitly enumerated
  - Invariant core items (principle number, severity, constraint-type, detection query structure) are concrete and well-chosen
  - Domain-specific items (examples, category names, compute references) correctly identified
  - 6-step task list provides a repeatable process
  - Output format specification is explicit (frontmatter + markdown rule file)
- **Gaps:**
  - No worked adaptation example - what does rule 1.1 look like before and after adaptation from aerospace to medical, or from code to legal?
  - No edge case handling: what if a domain-specific element turns out to be invariant in practice (e.g., a category name that exists identically across domains)? What if the source rule's examples are domain-neutral?
  - No failure mode documentation - what a bad adaptation looks like vs a good one
  - No cross-references to any example adapted rules in `ste-code/v2/core/rules/` or `ste-code/adapted/`
  - No criteria for verifying adaptation correctness - no quality gate, no self-check step
  - "Constraint logic" is in the invariant core list but "constraint-type" is also listed - unclear distinction
  - No guidance on how to identify when domain-specific vocabulary has no direct equivalent in the target domain (gap-filling strategy)
  - References `core/rules/{{rule_id}}.md` in loads-from - works for existing rules but no fallback for when a rule doesn't exist yet
- **What Level 3 Would Add:**
  - 1-2 full before/after adaptation examples (e.g., rule 1.1 aerospace → medical, or rule 3.2 aerospace → code)
  - Edge case protocol: domain-neutral elements, missing target equivalents, overlapping categories
  - Quality gate: after adaptation, verify all invariant core items survived unchanged, all domain-specific items were replaced, no new elements were invented
  - Cross-reference to at least one concrete adapted rule in the repo for reference
  - Distinction between "constraint-type" (invariant) and "constraint logic" (invariant) clarified or merged
- **Priority:** medium

### ste-code/v2/compute/prompts/compliance-check.prompt.md
- **Level:** 2
- **Summary:** Parameterized compliance checking prompt that applies rule subsets against documents using a 6-pass process, producing a scored compliance report with line-level corrections.
- **Strengths:**
  - Good parameterization: `document_type`, `target_domain`, `rule_subset`, `context_size` all documented with inline comment options
  - Context window budget awareness with three documented options (full/compact/minimal)
  - Explicit 4-step task breakdown
  - Output format is a complete markdown template with table columns for line, pass, original, corrected, principle, severity
  - "Unresolved" section acknowledges human-judgment cases
  - Compliance rubric file referenced with pass threshold (80/100)
- **Gaps:**
  - Cross-reference failure: `narratives/system-prompts/ste-code-full.md` does not exist at the relative `ste-code/v2/` path. The only copy lives at `SCE/narratives/system-prompts/ste-code-full.md`. The v2 narratives directory contains `ste-code-user.md`, `ste-code-micro.md`, `ste-code-developer.md`, and `ste-code-agentic.md` - none of which are named `ste-code-full.md`. A worker loading this prompt at the v2 root would get a missing file.
  - The 6-pass compliance check (Turn 0 → Turn 6) is referenced by name but never described - no summary of what each pass does, no rationale for the pass order
  - No worked compliance example - what does a real violation look like with its correction, principle mapping, and severity?
  - Severity assignment logic is missing - no rules for when a violation is blocking vs warning vs advisory
  - No guidance on handling overlapping violations (same line violates multiple principles)
  - No edge case protocol: what if corrected text is longer than original and breaks formatting? What if document is too large for the context window budget?
  - Compliance score formula is mentioned (pass threshold 80/100) but not explained - how are violations weighted?
  - `synonym_count` variable is referenced but not in the variables list at top
- **What Level 3 Would Add:**
  - Fix the `ste-code-full.md` path to either point to `SCE/narratives/system-prompts/ste-code-full.md` or create a v2 copy
  - 1-2 worked compliance examples with real violation text, corrections, principle mappings, and severities
  - Brief description of each pass in the 6-pass process (or inline the process if it's short)
  - Severity assignment rules tied to principles
  - Overlap resolution strategy for multi-principle violations on the same line
  - Add `synonym_count` to the declared variables list
  - Compliance score formula explanation
- **Priority:** high (broken cross-reference to mission-critical dependency file)

### ste-code/v2/compute/prompts/agentic-worker.prompt.md
- **Level:** 2
- **Summary:** Canonical template for generating per-worker prompt files in the STE-Code pipeline, with behavioral contract, rail enforcement, and state reporting.
- **Strengths:**
  - Clean variable design with 8 parameterized fields covering identity, stage, I/O paths, and batch coordination
  - Behavioral contract uses MUST/MUST NOT format - clear, enforceable, binary
  - Rails are enumerated with severity labels (critical/blocking) enabling priority-based enforcement
  - State report template is specific and self-contained - worker fills it out before finishing
  - Good structural fit for parameterized worker generation
- **Gaps:**
  - Rails are listed by code and name only (e.g., "R001 - No Fabrication (critical)") with no explanation of what behavior each rail actually requires or prohibits. A worker encountering "R001 - No Fabrication" has no concrete instruction for what constitutes fabrication in context.
  - No examples - no sample of a correctly completed state report, no sample of correct vs incorrect output
  - No failure recovery: what should a worker do if the source file is missing, unreadable, or empty? What if the output directory doesn't exist?
  - No cross-reference to `compute/agentic/gate-conditions.json` for the batch commit protocol referenced in R006
  - No cross-reference to `compute/agentic/anti-fabrication.json` for the fabrication rail R001
  - State report template has `{{turn_n}}` variable that is not in the declared variables list at top
  - Batch coordination is implicit - the template mentions "commit batch {{batch_n}} if all 3 workers complete" but doesn't explain how a worker knows whether sibling workers are done (gate conditions file check? coordination protocol?)
  - No timeout or staleness handling - what if a worker's output is stale by the time the batch commit runs?
- **What Level 3 Would Add:**
  - Inline rail explanations: 1-2 sentences per rail code describing the concrete prohibition and detection mechanism
  - 1-2 worked examples: a completed state report with real values, and a side-by-side correct vs fabricated output pair
  - Failure recovery protocol: source-missing → report and skip; output-dir-missing → create it; write-failed → retry once, then report
  - Cross-references to `compute/agentic/gate-conditions.json` and `compute/agentic/anti-fabrication.json`
  - Add `turn_n` to the declared variables list
  - Clarify batch coordination: reference to `compute/agentic/gate-conditions.json` for sibling completion checks
  - Self-verification step after writing: verify file exists, is non-empty, and contains no truncation markers
- **Priority:** high (central template used to generate all pipeline workers - gaps propagate to every generated worker prompt)
