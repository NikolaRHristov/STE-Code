# Maturity Audit - Batch F, Wave 3

## File Assessments

### ste-code/v2/narratives/system-prompts/ste-code-user.md
- **Level:** 3
- **Summary:** End-user guide teaching STE-Code to developers and technical writers. Covers core concept, 5 essential rules, a synonym quick-reference table, notice types (BREAKING/DEPRECATED/NOTE), extension procedure, and full-reference pointers.
- **Strengths:**
  - Clean hierarchical structure (What Is → Core Idea → Rules → Reference → Extension)
  - Concrete synonym table with 13 `Instead of... / Write...` pairs
  - Notice types (BREAKING, DEPRECATED, NOTE) are defined with actionable criteria
  - Cross-references to `ste-code-full.md`, `core/rules/`, `data/vocabulary/`, and `synonym-table.json`
  - Extension guidance includes file path, format, and review gate
  - Self-demonstrating: the document itself follows its own rules (short sentences, active voice, named code blocks)
- **Gaps:**
  - Synonym table is a curated excerpt, not the full table - no mention of how many total synonyms exist or where to find the complete list
  - No edge cases covered (e.g., what to do when a term appears in neither the approved nor synonym list)
  - No failure modes described (e.g., what breaks when an unapproved term leaks through)
  - The 5 rules are presented as a flat list with no rationale for why these 5 were chosen over the other 9 principles
  - No version indicator in the file (what version of STE-Code does this correspond to?)
  - Cross-references assume file paths but never verify they exist
  - No guidance on tooling - how does a user actually check compliance?
- **What Level 4 Would Add:**
  - Edge case handling: procedure for unclassified terms, mixed-domain documents, code blocks with embedded natural language
  - Design rationale for each of the 5 rules (why max 20 words for steps, why imperative mood matters for non-native speakers)
  - Full synonym table instead of excerpt, or explicit pointer with line count
  - Multiple examples per rule showing both violation and correction
  - Known limitations section (e.g., "This guide covers English documentation only; multi-locale is handled separately")
  - Tooling references: which linter/validator to use, CI integration snippet
- **Priority:** medium

### ste-code/v2/narratives/system-prompts/ste-code-micro.md
- **Level:** 2
- **Summary:** Compressed 2KB system prompt for low-context-window environments (sub-4K tokens). Contains the 5 most blocking rules, a one-line synonym quick-ref, and an output format template.
- **Strengths:**
  - Deliberately minimal and dense - achieves its stated goal
  - Rules are labeled with IDs (R1-R5) for traceability
  - Output format template is explicit (COMPLIANCE line, corrected text, CHANGES table)
  - Synonym quick-ref covers 8 pairs in a single line
  - Rule R3 (no noun-as-verb) is specific and includes concrete examples
- **Gaps:**
  - No examples of correct vs. incorrect output - user must infer from the output format template alone
  - No edge cases: what if a sentence is 21 words but can't reasonably be split? What if a framework name (allowed) looks like a verb?
  - "Approved vocab only" lists 17 categories but doesn't explain them - what are "roles", "UI terms", "spec files" in this context?
  - No cross-references at all except a file path to `data/synonyms/synonym-table.json`
  - Doesn't explain why these 5 rules were chosen over the other 9 principles
  - No guidance on when to switch to the full prompt vs. staying on micro
  - No version history beyond "v1.0" in the title - is this v1.0 of the micro prompt or v1.0 of STE-Code?
  - R1's approved categories list is ambiguous: are "runtime conditions" things like race-condition and deadlock, or runtime environments?
- **What Level 3 Would Add:**
  - One complete before/after example showing a non-compliant paragraph and its corrected form
  - Clarification of each approved category with 1-2 examples per category
  - Cross-reference to the full prompt (`ste-code-full.md`) with a decision rule for when to use which
  - Edge case guidance: what to do when you can't satisfy R4 (sentence length) without breaking R2 (one term per concept)
  - Version tracking: which version of the full ruleset this micro prompt was derived from
- **Priority:** high

### ste-code/v2/narratives/system-prompts/ste-code-developer.md
- **Level:** 3
- **Summary:** Developer guide for extending, adapting, and tooling the STE-Code standard. Documents the four-stratum architecture, provides step-by-step procedures for adding rules, vocabulary, domains, agentic rails, and prompt templates, and defines stratum isolation rules.
- **Strengths:**
  - Architecture diagram clearly separates concerns (core/data/compute/narratives)
  - All 5 extension procedures are numbered step-by-step with specific file paths
  - Schema validation commands are copy-paste ready with real file globs
  - Stratum isolation rules are explicit and directional (e.g., "core/ never imports from data/")
  - Domain adaptation procedure correctly scopes adapted rules to a subdirectory
  - Prompt template procedure includes frontmatter variable declaration and loads-from requirements
- **Gaps:**
  - No examples of actual rule files, vocabulary entries, or frontmatter - procedures describe what to create but never show what it looks like
  - No common failure modes (e.g., "rule N.N references a term not yet in vocabulary" or "synonym table entry conflicts with an approved term")
  - No testing or verification step after any procedure - how do you know the new rule actually works?
  - Stratum diagram is ASCII-only, no explanation of the compute layer's role beyond a one-line description
  - No version compatibility guidance - if I add a rule to core/, which narrative files need regeneration?
  - "Update the narrative files that reference principle counts" is vague - which files, and is there a script for this?
  - No troubleshooting section or FAQ
  - Missing cross-reference to the agentic prompt for rail development despite mentioning `ste-code-agentic.md`
- **What Level 4 Would Add:**
  - Annotated examples: a real rule file excerpt, a real vocabulary entry with domain tags, a real prompt template with frontmatter
  - Common failure modes table with symptoms, causes, and fixes
  - Validation/testing step in every procedure (e.g., "Run `npx ajv` and confirm 0 errors")
  - Design rationale for stratum isolation - why does this architecture prevent bugs?
  - A "What breaks when you get this wrong" section for each procedure
  - CI pipeline reference: where do these validations run, what's the failure threshold?
  - Versioning guidance: semantic versioning for rule changes, vocabulary additions, narrative regeneration
- **Priority:** medium

### ste-code/v2/narratives/system-prompts/ste-code-agentic.md
- **Level:** 3
- **Summary:** Agentic system prompt for pipeline workers in the STE-Code extraction/refinement/adaptation pipeline. Defines 8 hard rails with severity levels, GATE transition conditions, worker lifecycle, commit message format, state report format, and an anti-fabrication checklist.
- **Strengths:**
  - Rails table includes ID, description, severity (critical/blocking), and on-violation behavior
  - GATE conditions include concrete thresholds (434 files, 109 extracted, 500KB, 51 adapted files)
  - Worker lifecycle is a numbered 7-step procedure covering the full turn
  - Commit message format has a template and an example
  - State report format is a structured markdown template with all required fields
  - Anti-fabrication checklist has 5 explicit items with traceable IDs (AF-01 through AF-05)
  - Severity classification is explicit (critical = halt, blocking = flag and continue)
- **Gaps:**
  - Rails have severity but no priority or resolution ordering - what if R001 and R007 fire simultaneously?
  - No examples of actual violation handling - what does "halt, flag R001" produce as output?
  - Gate conditions reference `compute/agentic/gate-conditions.json` but don't describe what happens when a gate assertion fails (retry? escalate? skip?)
  - Worker lifecycle step 6 ("every 3 workers") is arbitrary - no rationale for batch size of 3
  - State report template references `agent-id` and `stage-name` but doesn't enumerate valid values
  - No recovery procedure for workers that die mid-batch - how does Continuator pick up?
  - Missing cross-reference to the developer guide for how to add/modify rails
  - No version indicator on the rails themselves - are rails versioned independently of the prompt?
- **What Level 4 Would Add:**
  - Rail conflict resolution order and examples of multi-rail violations
  - Example of a complete state report from a real worker turn
  - Recovery procedures: what the Continuator agent needs to resume after a rail halt
  - Design rationale for batch size of 3, gate thresholds, and severity assignments
  - Cross-reference matrix: which rails protect which pipeline stages
  - Rail versioning: how to add a new rail without breaking existing worker contracts
  - Edge case: what to do when a gate condition is met but quality is suspect (e.g., 109 files exist but some are 0 bytes)
- **Priority:** high

### ste-code/v2/narratives/examples/example-readme.md
- **Level:** 2
- **Summary:** Before/after example of an STE-Code compliant README. Shows a non-compliant paragraph alongside a violation table (line, original, corrected, principle), the corrected version, and a "What Changed" summary.
- **Strengths:**
  - Before/after comparison is side-by-side and clearly formatted
  - Violation table is granular - 8 violations mapped to specific principles
  - "What Changed" summary lists every substitution with its synonym category
  - Self-demonstrating: the corrected README is itself STE-Code compliant
  - Document metadata header declares compliance score and principles applied
- **Gaps:**
  - Single example only - one README style, one violation pattern, one document type
  - Principles are referenced by ID (P1, P2, P12) but never explained - reader must look them up elsewhere
  - No edge cases covered: what about READMEs with tables, badges, contributor sections, license blocks?
  - The "Before" text is artificially bad - no real-world README looks like this, reducing transferability
  - No language-identifier edge case shown (all code blocks are bash - what about python, javascript, yaml?)
  - No cross-references to the specific rule files or the user guide
  - Missing: what to do with emoji, images, links, or multi-paragraph descriptions
- **What Level 3 Would Add:**
  - At least 3 examples covering different README styles: micro-library, full-stack app, CLI tool
  - Principle-by-principle walkthrough explaining why each correction was made
  - Edge case examples: mixed-language code blocks, badge-heavy READMEs, monorepo READMEs
  - Cross-references to the specific rules in `core/rules/` that each principle maps to
  - A "Common Mistakes" section with 3-5 recurring violation patterns and their fixes
  - Guidance on how to progressively migrate an existing README (partial compliance is acceptable)
- **Priority:** high

### ste-code/v2/narratives/examples/example-commit-message.md
- **Level:** 2
- **Summary:** Example file demonstrating STE-Code compliant commit messages. Defines 5 commit message rules and provides 3 before/after pairs covering feat, fix, and BREAKING CHANGE commit types.
- **Strengths:**
  - 3 examples covering distinct commit types (feat, fix, BREAKING)
  - Commit rules are explicit and actionable (imperative mood, max 72 chars, approved verb)
  - BREAKING CHANGE example includes version, migration path, and a concrete code change instruction
  - Before examples are humorously bad ("whoops, nuked the old migration") making the contrast clear
  - Rule 4 (one change per commit) is stated but not force-demonstrated in the examples
- **Gaps:**
  - Only 3 commit types covered - missing: docs, chore, ci, test, refactor, revert, merge, perf, style, build
  - No edge cases: multi-paragraph bodies, co-authored commits, merge commits with conflict resolution notes, reverts of reverts
  - Character limit (72 chars) is claimed but never verified in the examples - are the subjects actually ≤ 72?
  - No cross-references to the synonym table or vocabulary - which verbs are "approved" for dev-operations and data-operations?
  - Rule 5 (BREAKING CHANGE) is demonstrated but Rule 4 (one change per commit) is stated without an example showing a violation
  - Conventional Commits format is assumed but never explained - what does `feat(cache):` syntax mean?
  - No guidance on commit message body structure beyond "max 25 words per sentence"
- **What Level 3 Would Add:**
  - Examples covering at minimum: docs, chore, ci, test, refactor, revert, perf - at least 8 commit types total
  - Edge case examples: multi-paragraph bodies, co-authored-by trailers, merge commits
  - Cross-reference to the approved verb list in the synonym table
  - A "Common Mistakes" section with violations and why they matter
  - Verification: a note that `git log --oneline` or commit hooks can enforce these rules
  - Explicit mapping of approved verbs to commit types (e.g., `read` for docs, `repair` for fix, `build` for ci)
- **Priority:** high

## Batch Summary
- Files scored: 6
- Level distribution: -2:0 -1:0 1:0 2:3 3:3 4:0 5:0
- Highest priority: `ste-code/v2/narratives/system-prompts/ste-code-micro.md`, `ste-code/v2/narratives/system-prompts/ste-code-agentic.md`, `ste-code/v2/narratives/examples/example-readme.md`, `ste-code/v2/narratives/examples/example-commit-message.md` - all four are Level 2 and need examples, edge cases, and cross-references to reach Level 3
- Pattern observations:
  - **Example files are the weakest tier.** Both `example-readme.md` and `example-commit-message.md` are Level 2 despite being the files users will reach for first. They need 3-5x more examples and edge case coverage to be trustworthy references.
  - **Synonym/vocabulary references are inconsistent across files.** The user guide has 13 synonym pairs, the micro prompt has 8, and neither references the canonical source with a line count or version. No file explains the full vocabulary size or scope.
  - **No file reaches Level 4+.** None of the 6 files include edge case handling, failure recovery procedures, design rationale, performance considerations, or known limitations. The ceiling across this batch is Level 3.
  - **Cross-references are one-directional.** Files reference targets (e.g., `core/rules/`, `data/synonyms/synonym-table.json`) but never verify those targets exist or describe what the reader will find there. The developer guide references `ste-code-agentic.md` for rail development but the agentic prompt doesn't link back.
  - **Version and lineage are untracked.** Only the micro and agentic prompts have version labels (v1.0). The user guide, developer guide, and both example files have no version indicator, making it impossible to know which revision of the standard they correspond to.
  - **Agentic prompt is the most under-documented Level 3.** Its rails and gates are well-structured but have zero examples of violation output, recovery procedures, or conflict resolution - critical gaps for a file that pipeline agents execute against.
